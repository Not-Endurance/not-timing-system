# REST API

Endpoints follow JSON:API 1.1 (jsonapi.org). Only the grammar of `filter` is borrowed from OData. The reasons are in ADR-0008. A resource that has not been ported yet is legacy and keeps its shape (list at the end).

## Routes

- A collection is a plural kebab-case noun: `/events`, `/user-sessions`. An item is `/events/{id}`.
- Event-scoped resources stay flat and carry `eventId` as an attribute: `/participations?filter=eventId eq 3f2504e0-4f89-41d3-9a0c-0305e82c3301`.
- The method carries the meaning: POST creates (201, `Location`), GET reads, PATCH changes members (200 with the resource), DELETE removes (204).
- A named collection is a GET-only view of one resource type that the glossary names: `/events/live`, `/events/historic`. It returns the same resource type, each item's `self` link points at the canonical item URL, and it takes the same query parameters. Every other narrowing uses `filter`.
- Model an operation as a create, update or delete of a resource: starting an Event is `POST /events` naming the configure event, resetting one is `DELETE /events/{id}`. An operation whose effect differs from its method's default meaning shows its intent in the path, `POST /{collection}/{id}/actions/{verb}`, and is noted in this file.

## Documents

- Media type `application/vnd.api+json` on both `Content-Type` and `Accept`.
- A resource object is `{ "type": "<collection>", "id": "<string>", "attributes": { ... } }`. The id is a string on the wire and a Guid in the domain (ADR-0009).
- Members are camelCase. Foreign keys are plain attributes (`eventId`, `participationId`). `relationships` and `include` wait for a consumer that needs them.
- Values the server computes (`isLive`) are read-only attributes; writes ignore them.

## Status and errors

- 200 read or update. 201 create. 202 taken, and the outcome is not told. 204 delete. 400 malformed request, filter or parameter. 401 not signed in. 403 not allowed. 404 missing item. 409 conflict with current state. 413 body of more than 1 MiB (`payload-too-large`). 422 domain rule violated. 429 too many requests (`rate-limited`, with the seconds to wait in `Retry-After`). 500 unexpected. An empty collection is 200 with `"data": []`.
- Every error is `{ "status", "code", "title", "detail"? }` in `errors`. `code` is a stable kebab-case identifier (`event-ended`) that clients branch on. `title` and `detail` are for people and change with the wording.
- The status always reports the outcome.

## Query parameters

- `filter` holds one OData `$filter` expression: `filter=eventId eq 3f2504e0-4f89-41d3-9a0c-0305e82c3301 and isNotRanked eq false`. A Guid is written unquoted, as the OData grammar has it, a string is quoted with its quotes doubled (`name eq 'O''Brien'`), and the members are the resource's in camelCase, a member of what a resource embeds by a path (`country/isoCode eq 'BG'`). The server maps the expression onto `ODataQueryOptions` and applies it to Mongo LINQ (`ReferenceQuery`). An expression that is not valid, or names a member the resource has not or keeps to itself, is 400 `invalid-filter`.
- `sort` lists members, `-` prefix for descending (`sort=-name,id`). It maps to `$orderby`; one that is not a list of members of the resource is 400 `invalid-sort`. A list that is not sorted is in the order of the ids, so that its pages do not overlap.
- `page[size]` (1 to 500, 100 when it is not named) and `page[number]` (from 1) cut a list into pages: 400 `invalid-page` for any other. The answer says which page it is in `meta.page` (`size`, `number`) and where the next one is in `links.next`, which is not there on the last. A collection that can outgrow one screen takes them.
- `fields[...]`, `include` and any other parameter answer 400 `unsupported-parameter` until a consumer needs them.
- The families of reference data take the whole grammar (the next section). `JsonApiQuery` still reads the part of it that the other routes use: members compared with `eq` and joined by `and`, for the members the route names. Any other expression, and any member the route does not name (the owner of a record, say), is 400 `invalid-filter`.
- A search is a read that takes `filter=contains(name,'text')` and nothing else (`JsonApiQuery.ReadSearch`): the text is matched as it is written, in any case, a quote in it is doubled (`d''arcy`), and it is at least three characters (400 `search-too-short`). A search is not a listing, so one with no filter, another member or another expression is 400 `invalid-filter`, and it answers at most ten matches. No route takes a parameter that names a Tenant or asks for every Tenant (`tenantId`, `allTenants` and the like are 400 `unsupported-parameter`, or ignored by a route that reads no parameters); what reaches across Tenants is a named view, below.

## Authorization

- Every route requires a signed-in caller unless it is on the public-read allowlist (ADR-0012): one list in the Api (`PublicEndpoints`), enumerated by a test (`DenyByDefaultTests` lists the real endpoints against it), read-only, and never a write. An unauthenticated caller gets 401 `not-signed-in`, never a redirect; a signed-in caller who may not do it gets 403 with a code such as `not-main-operator`. The rule is applied in one place, before any endpoint runs (`AccessBaseline`, `AccessBaselineMiddleware`): a route is public only because the list names it, and declaring it anonymous on the route does nothing, so a new route is protected until someone adds it to the list and to the test.
- The list has two kinds of entry. Public reads are views (`/healthz`, the Ui, the live hub and its negotiation, which only push what any viewer may see and have no method a client can call) and the answer to an unknown API route, a 404 for everybody. The sign-in surface (`/sign-in`, `/register`, `/privacy`, `/account/passkeys`, their assets, and the routes below that make a caller) is anonymous by nature.
- A write to a protected route sends the header `X-Requested-With: NoTiming`, or it is 400 `request-header-required`. A browser sends a header like that to another origin only after the origin has allowed it, which the CORS policy refuses, so another site (or a sibling subdomain, which SameSite does not keep out) cannot write with a visitor's cookie. The pages of the Api and the Ui send it on every write; a client that is not a page sends it too. The sign-in surface needs no header, because nobody is signed in yet.
- Repositories filter by the current Tenant by default (ADR-0012, #643). Every collection that a Tenant owns is read and written through `TenantCollection`, which joins every filter with the current Tenant, stamps what it writes and never moves a document from one Tenant to another; with no current Tenant a read finds nothing and a write is refused. The current Tenant is the Event's inside an Event, and elsewhere the Tenant the account has selected, or its home Tenant (`GET /api/me` says which). A cross-tenant read is a named view of its collection, never a parameter a caller can send to any resource; the ones there are: an Event by its id, the Events a Main Operator runs, `/api/{athletes,horses,clubs,officials}/all-tenants` and `/api/accounts/all-tenants`, and the public lists of Events (`/events/live`, `/events/historic`, with the Events resource). They are the only places that open such a collection without a Tenant (`CrossTenantReads`, `GrantInvitations`).
- What a caller may do is decided by one pure function of the domain (`AccessPolicy`, the access matrix of ADR-0012) over facts the server reads: the caller's roles, the Event's Tenant, Main Operator and stage, and what the caller has been granted on the Event. Every write route and `GET /api/events/{id}/capabilities` ask it and nothing else, and it answers with the reason that is missing, which the Api gives a status and a code: 401 `not-signed-in`; 403 `not-allowed`, `not-tenant-root`, `not-main-operator`, `not-developer`; 409 `tenant-not-operational`, `event-not-started`, `event-started`, `event-ended`. The role is checked before the stage of the Event, so a person who may not do it is only told that.
- There are no anonymous route groups. The sign-in routes below are the only writes that are anonymous: a person signs in to become a caller.
- A write sends `Content-Type: application/vnd.api+json`, and nothing else is read (415 `unsupported-media-type`). A browser may not send that type to another origin without a preflight, which the CORS policy refuses, so another site cannot write with a visitor's cookie. A body that is not one resource of the expected type is 400 `malformed-request`, and one of more than 1 MiB is 413 `payload-too-large`, before it is read.
- A record that belongs to a caller is found by owner only: a route names no owner, the store has no operation without one, and the record of another person is answered 404 `not-found`, exactly as a record that does not exist is.

## Authentication

A person signs in with a code sent by email or with a passkey, and the session is a cookie the server sets (ADR-0002). The cookie is `__Host-NoTiming`: host-only, HttpOnly, Secure, SameSite=Lax, persistent, 30 days sliding, and it carries only the key of a ticket the server keeps. The pages that use these routes are `/sign-in`, `/register`, `/privacy`, `/account/passkeys` and their assets, served by the Api; the Ui links to them.

- `POST /api/code-challenges` with `{ "email" }` asks for a code. It answers 202 with no body whether or not the address has an account, and inside the resend cooldown of the previous code, so the answer tells nothing; a malformed address is 400 `invalid-email`.
- `POST /api/registrations` with `{ "email", "givenName", "surname", "countryId", "website"? }` registers a new person (#601): 202 with no body, a code is mailed, and nothing is stored until the code comes back to `POST /api/sessions`, which then creates the account (confirmed address, the names, a home Tenant from the country, one membership in it) and signs it in. It answers alike for an address that has an account (that address is sent a sign-in code and what was typed is dropped), for one on a cooldown, for one a configured allow-list keeps from registering (`Registration:AllowList`: addresses and `@domain` entries; staging is closed without one, production is open without one) and for a body that fills `website`, the field of the page that people never see, which only a program fills in. A malformed address is 400 `invalid-email`, a missing, too long (100 characters) or control-character name 400 `invalid-name`, a country that is not one of those the page lists (it needs an ISO code) 400 `invalid-country`. The page lists the countries from the `countries` collection. Every 202 also sets `__Host-NoTiming-Registration` (HttpOnly, Secure, SameSite=Strict, 15 minutes, the same value for a browser that sends it back): its secret is hashed into the details that wait in the challenge, and they are used only when the code comes back with the same cookie. A code that comes back without it, from another browser, still proves the address and opens the account, without the names, the country and the home Tenant: whoever asked for a code for an address first cannot choose the account its owner gets.
- `POST /api/sessions` with `{ "email", "code" }` signs in: 201, the `sessions` resource `current` (`method`: `code` or `passkey`, and `passkeyCount`, which the sign-in page uses to decide whether to offer one) and the cookie. A wrong, spent, expired or exhausted code is 401 `invalid-code`, whatever the reason. With `{ "credential" }`, the assertion a passkey made as the browser's WebAuthn API serialises it, the same route signs in with a passkey; one that signs nobody in is 401 `invalid-passkey`, whatever the reason.
- Asking for a code (`/api/code-challenges` and `/api/registrations` alike) and trying one are rate limited, per host and per hour (`Auth:RateLimits`): a request draws on the budgets of its address (5), its client (10, a client being the forwarded address, an IPv6 one by its /64) and the platform (100); a wrong code draws on those of the address as that client tries it (5), the client (10) and the platform (100), and a right code costs nothing. A request that is out of a budget is 429 `rate-limited` with `Retry-After`, before the address is looked at, so it is the same for every address, and it costs nothing. A malformed request is not counted.
- `DELETE /api/sessions/current` signs out: 204, the ticket is deleted and the cookie cleared. Without a session it is 204 as well.
- `GET /api/me` is the `accounts` resource of the caller (`email`, `emailConfirmed`, `name`, `passkeys`, `profileComplete`, `homeTenantId`, `selectedTenantId` and `currentTenantId` when there are ones, `memberships` (each `tenantId` and its `roles`) and `isDeveloper`), or 401 `not-signed-in`. A route that needs a caller answers 401 with that code, never a redirect. `PATCH /api/me` changes one member, `selectedTenantId`: the Tenant that what the caller reads and writes belongs to outside an Event, null to go back to the home Tenant. It has to be one the caller is a member of (the Developer may act in any Tenant that exists), or it is 422 `not-a-member`; any other member is 400 `unsupported-attribute`. No route gives a role or the Developer flag: `tenant-root` and `IsDeveloper` are written by the Developer's commands (`seed-tenant-root`, `grant-developer` in `tools/NTS.Tools`).
- `GET /api/me/profile` and `PATCH /api/me/profile` are the profile of the caller (#602), the `profiles` resource whose id is the account's: `givenName`, `middleName`, `surname`, `countryId` (the country its `countryRegion` names, when one of ours does), `countryRegion`, `club`, `feiId` and the computed `complete`. The routes name no account, so there is no way to reach another: a document that names an id that is not the caller's is 409 `profile-id-mismatch`. A PATCH names the members it changes: one that is not named stays, and an optional one that is null or blank is cleared. `givenName` and `surname` are required and `countryId` is the id of a country that has an ISO code; a value that is not valid (a name, club or FEI ID longer than 100, 100 and 20 characters, or with a control character, a country that cannot be chosen) is 400 `invalid-name`, `invalid-club`, `invalid-fei-id` or `invalid-country`, and a profile that would lack a country, a first name or a surname is 422 `profile-incomplete`; nothing is saved when either happens. The edit sets only the fields of the profile (the name is rebuilt from the three names): it never moves the home Tenant, though an account that has none is placed when it first picks a country.

### Passkeys

A passkey is a resource of the signed-in person: `/api/passkeys`, with its credential id in base64url as the id. They are discoverable, require user verification and are never attested; the relying-party ID is configuration (`Passkeys:RelyingPartyId`, `localhost` in Development), and a host with none answers 503 `passkeys-not-configured` on every route below that needs one.

- `POST /api/passkeys/actions/request-options` (anonymous) answers the options for `navigator.credentials.get`, and `POST /api/passkeys/actions/creation-options` (signed in) those for `navigator.credentials.create`, which exclude the passkeys the person has. Both are actions in the sense above: they create nothing, and they hold the challenge in a short-lived host-only cookie that the next call consumes.
- `POST /api/passkeys` with `{ "credential", "name"? }` stores the passkey the browser made: 201 and the resource, and a "new passkey added" email in the language of the request (a mail that cannot be sent is logged and does not undo the passkey). A credential that does not verify, or arrives with no ceremony underway, is 400 `invalid-passkey`.
- `GET /api/passkeys` lists them. `PATCH /api/passkeys/{id}` renames (`name`). A name is at most 60 characters, on both routes: longer is 400 `invalid-name`. `DELETE /api/passkeys/{id}` removes: 204, and the last passkey is 409 `last-passkey`, because losing the device would lock the person out. A passkey is looked up among the caller's own: someone else's, or none, is 404 `not-found`.
- The ceremony routes (the two actions, `POST /api/passkeys`, and `POST /api/sessions` with a credential) verify an antiforgery token on top of the media type: the header `X-XSRF-TOKEN` carries the token the server put into the page, and the cookie that goes with it is `__Host-NoTiming-Xsrf` (unprefixed and not Secure-only in Development, which runs on plain http). A request without a matching pair is 400 `antiforgery-token-invalid`.

### Session state

What a person keeps per Event (the Snapshots they have sent and the ones they have selected) is the `user-sessions` resource (#602), flat, with the Event as the attribute `eventId` and the state as the member `state` (`snapshotHistory`: groups of `entries` and a `type`, and `snapshotSelections`; enums are their names). It is the caller's own: the routes name no owner, the store finds records by owner only, and a record of another person is 404 `not-found`, exactly as one that does not exist is.

- `GET /api/user-sessions` lists the caller's records and takes the filter `eventId eq <id>`; the owner cannot be named in it (400 `invalid-filter`), and `sort`, `page`, `fields`, `include` and any other parameter are 400 `unsupported-parameter`. `GET /api/user-sessions/{id}` reads one.
- `POST /api/user-sessions` with `{ "eventId", "state"? }` makes the caller's record for the Event, or returns the one they have: 201 with `Location` the first time and 200 after, and a state offered to a record that exists is not put over it. The id is the server's: a document that brings one is 403 `client-id-not-supported`, and an Event id that is not one is 400 `invalid-event`.
- `PATCH /api/user-sessions/{id}` replaces `state`. The Event of a record does not change: naming another is 409 `event-immutable`. `DELETE /api/user-sessions/{id}` removes the record: 204.
- What is stored is what the Functions API stores (PascalCase members, enums as text, no null member, the constant Tenant `nts` until the Tenants of ADR-0012 reach the data), so the records that exist read the same; the owner is the account id. The legacy routes that list or read by a user identifier, which let anyone read anyone's, have no equivalent.

### Tenants

- `GET /api/tenants/{id}` is the `tenants` resource, whose id is the key of its kind and country (`country-bg`, a text and not a Guid): `name`, `kind`, `isOperational` (it has a Tenant Root, which the Developer's command gives) and `regionalRules` (`onlyAverageLoopSpeed`, and `rankerCode` when there is one), for any signed-in caller; an unknown Tenant is 404. `PATCH /api/tenants/{id}` edits the rules, which an Event copies when it starts and never reads from the Tenant again: a Tenant Root of the Tenant, or the Developer (403 `not-tenant-root` for anybody else). The members it names are merged into the rules (not named stays, a null `rankerCode` clears it), rules that are not valid are 400 `invalid-rules`, and a member of the Tenant other than `regionalRules` is 400 `unsupported-attribute`.
- `GET /api/tenants/{id}/capabilities` is the `capabilities` resource of the Tenant for the caller (`canCreateEvents`, `canEditRules`, `canEditBranding`, `canEditRegistry`, `canSearchAccounts`), from the same policy.

### Events and who runs them

An Event belongs to one Tenant and has one Main Operator (ADR-0012). Both are fields of its document, the Setup's before it starts and the Core's after, and they travel with it when it starts. Whether it is Live is a rule of its end and the clock of the host (`EventStageRule`, ADR-0007), never a stored flag; the stage is `unstarted`, `live` or `historic`.

- `POST /api/configure-events` with `{ "name", "location", "feiShowId"? }` makes an Event in the Tenant the caller acts in and makes the caller its Main Operator: 201, its `Location` and the `configure-events` resource (`name`, `location`, `feiShowId`, `tenantId`, `mainOperatorId`). The document may name the id of the Event (`data.id`, a Guid), as a client that makes its ids does; the same id again is that Event, 200, and an id that another Tenant's Event has is 409 `id-taken`. A Tenant Root of that Tenant, or the Developer (403 `not-tenant-root`); the Tenant has to be operational (409 `tenant-not-operational`, the Developer included) and its country has to be among the countries (409 `tenant-country-missing`); with no current Tenant it is 409 `no-current-tenant`. A name or location that is blank, longer than 100 characters or of more than one line is 400 `invalid-name` or `invalid-location`. The Event cannot be given a Tenant or a Main Operator, or any member but these three: that is 400 `unsupported-attribute`. The rest of the Setup, and the read of it, are the Setup's own routes.
- `POST /api/events/{id}/actions/assign-main-operator` and `POST /api/events/{id}/actions/hand-over`, each with `{ "accountId" }` in a `main-operators` document and nothing else (any other member is 400 `unsupported-attribute`, a missing or malformed `accountId` is 400 `malformed-request`), change the Main Operator: 204. Assigning is a Tenant Root of the Event's Tenant (or the Developer) while the Event has not started, and once it is Live it is 409 `event-started`; handing over is the current Main Operator alone, while the Event is Live (403 `not-main-operator` for anybody else, a Tenant Root and the Developer included; 409 `event-not-started` or `event-ended` at the other stages). The account has to exist (422 `account-not-found`); it is named by its id, found by name through the search below, so no route tells whether an email has an account.
- `GET /api/events/{id}/capabilities` is the `capabilities` resource of the Event for the caller: `stage`, `isMainOperator`, `canSnapshot`, `canHandOver`, `canAssignMainOperator` and `canCreateEvents` (in the Event's Tenant). It is the policy's own answer for the caller and the Event as they are now, so what a screen offers and what the server accepts cannot differ. An Event that is not there, or an id that is not one, is 404.

### Grants

The Main Operator links people to the Officials and Operators of its Event: the `event-grants` resource, flat, with the Event as the attribute `eventId` (ADR-0012). A grant is in the Tenant of its Event and gives Snapshot access to an Operator, and to an Official of a role that may (Steward, ChiefSteward, GroundJury, GroundJuryPresident); any Official is Staff and sees how times were recorded.

- `POST /api/event-grants` with `{ "eventId", "kind", "officialRole"?, "email" | "accountId" }`: `kind` is `operator` or `official` (400 `invalid-kind`: never a role of the Tenant or of the platform), `officialRole` is a role of the domain by its name for an Official and none for an Operator (400 `invalid-role`), and the person is named by an email (400 `invalid-email`) or by an account (422 `account-not-found`) and by one of them. 201 and the grant, or 200 and the one that was made before: the same person in the same kind and role is one grant. An email that has an account gives it the grant at once; one that has none is a pending invitation (`pending: true`), which gives nothing and attaches to the account that registers with that email, or signs in with a code to it. The Main Operator of the Event, or the Developer before it starts (403 `not-main-operator`); 409 `event-ended` for an Event that has ended; 404 for one that is not there. An Event holds at most 500 grants: one more is 422 `grant-limit-reached`, though a grant it has is still answered with 200. Attaching a pending invitation to the account that signs in never fails the sign-in: when the grants cannot be written it is logged and tried again at the next sign-in.
- `GET /api/event-grants?filter=eventId eq <id>` lists the grants of one Event for its Main Operator or the Developer, whatever the stage; there is no listing without the Event. `DELETE /api/event-grants/{id}` removes one, and the access ends with it: 204, and to anybody who is not the Main Operator of its Event it is 404, as it is for one that does not exist. A grant's attributes are `eventId`, `kind`, `officialRole`, `pending`, `accountId` and `displayName` when there is an account, and an `email` that is partly masked (`a***@example.test`): an address never comes back whole.

### The Event

An Event is the `events` resource once it has started (#628, ADR-0007). Until then it is a Setup (`configure-events`), which is not an Event: it is not found here.

- `GET /api/events`, `GET /api/events/live`, `GET /api/events/historic` and `GET /api/events/{id}` are public reads of the Events that have started, of every Tenant (they are on the public list of ADR-0012, and read-only). The two named collections split the Events by the clock of the host, return the same `events` resources, link each item's `self` to `/api/events/{id}`, and take the parameters of every list (`filter` over the members of the Event, `sort`, `page[...]`); an expression that is valid but that the data cannot run, such as `year(endDay)`, is 400 `invalid-filter`. An id that is not an Event's, or is a Setup's, is 404.
- An Event shows `name`, `location`, `country`, `feiShowId`, `startDay`, `endDay`, `tenantId`, `regionalRules` (the rules of the Tenant when it started) and the read-only `isLive`, which is `true` until the end of its last day and `false` from the second `endDay` names, with no grace, and is told by the clock and never stored. Who runs it is not shown.
- `POST /api/events` starts an Event from its Setup. The document names the Setup as the id of the resource and takes nothing else: `{ "data": { "type": "events", "id": "<the id of the Setup>", "attributes": {} } }` (400 `id-required`, `invalid-id`, `unsupported-attribute`; 404 for a Setup that is not there). It is 201, its `Location` and the resource, or 200 and the Event that was started when the same Setup is started again. It is the Main Operator's, and the Developer's before it starts, which is the policy row of configuring an Event (403 `not-main-operator`; 409 `event-ended` for an Event that is over; 409 `tenant-not-found` for a Setup whose Tenant is gone). The Event keeps the Tenant and the Main Operator of its Setup and the rules of its Tenant as they are then, copies the Officials and the Operators, and creates the Participations and the Rankings of its competitions. A Setup that is not whole is 422 `invalid-setup`, one that configures the FEI export in part is 422 `incomplete-fei-configuration`, each with what is missing in `detail`, and one an Event cannot be made of is 422 `invalid-attribute`. A start that fails leaves no Event behind.
- `PATCH /api/events/{id}` changes the members it names (`name`, `location`, `country`, `feiShowId`, `startDay`, `endDay`; null takes a member away) for the Main Operator and while the Event is Live (403 `not-main-operator`; 409 `event-ended`; an Event that has not started is 404). The days are whole days in the offset they are given in, and an Event is over when its last day is, so changing its days cannot end it, and cannot make it start after its last day (422 `invalid-attribute`). Its Tenant, its Main Operator and its rules are not written (400 `unsupported-attribute`).
- `DELETE /api/events/{id}` resets an Event to its Setup, for the Main Operator and while the Event is Live (403 `not-main-operator`; 409 `event-not-started` or `event-ended`). It removes what the Event made, what was kept for it (the state of a person, the Snapshots still waiting) and the Event itself, last, so that a reset that stopped is made again by making it again: 204.

### Reference data and the Setup

The Clubs, Horses and Athletes of a Tenant's registry, the countries of the platform and the Setup of an Event move as JSON:API resources (#603, ADR-0008): `clubs`, `horses`, `athletes`, `countries` and `configure-events`. The routes of the first four are the same (`ReferenceEndpoints`), over a model of the domain whose members are the attributes, in camelCase, nulls left out, with the id as the resource's own. The client reads and writes them through the JSON:API variant of its repository (`JsonApiRepository`, `JsonApiClient`), which pages through a list, writes a member that is null as null (on a change it is a member taken away), and reads an error with its `code` (`LastError`).

- `GET /api/{type}` lists, with `filter`, `sort` and `page[...]` above; `GET /api/{type}/{id}` reads. Any signed-in account reads, the rows of the Tenant it acts in: a row of another Tenant, a missing one and an id that is not a Guid are alike 404 `not-found`, and an account with no current Tenant lists nothing. The countries are the platform's, so every account reads all of them. Nobody who is not signed in reads any (401).
- `POST /api/{type}` makes a row and answers 201 with the resource and its `Location`. The document may name the id (`data.id`, a Guid), as a client that makes its ids does: the same id again is the row that was made, 200 and the first outcome, and an id that another Tenant's row has is 409 `id-taken`; with no id the server makes one. Members the server owns (`tenantId`) or keeps to itself, and members the resource has not, are 400 `unsupported-attribute` and nothing is written; a member of another type is 400 `malformed-request`; a row the domain does not accept (a blank name, an Athlete with no Country, a FEI ID that is not a number) is 422 `invalid-attribute` with the member in `detail`.
- `PATCH /api/{type}/{id}` changes the members the document names and no others (200 and the resource); a member sent as null is taken away. A document that names another id is 409 `id-mismatch`. `DELETE /api/{type}/{id}` removes (204), and a row that is not there, or is another Tenant's, is 404. The countries are not removed: there is no route, because Events and Athletes embed one.
- Who writes: a Tenant Root of the Tenant and the Main Operator of an Event of it that is not yet Historic, or the Developer, for Clubs, Horses and Athletes (403 `not-allowed`; the policy's `EditRegistry`); the Developer alone for the countries (403 `not-developer`). An account with no current Tenant cannot write a registry (409 `no-current-tenant`).
- An Athlete embeds its `country` and its `club`, which can be filtered on (`country/isoCode`). Its link to an account holds an email and more, and is the server's alone: `user` is not shown, not taken, and not in the grammar of `filter` or `sort`, so no route says which account a rider is linked to and no filter finds a rider by an address. An edit of an Athlete leaves the link as it was.
- `GET /api/configure-events/{id}` reads the Setup of an Event: the Main Operator, a Tenant Root of the Tenant that holds it and the Developer, at any stage (403 `not-allowed` for anybody else, 404 for an id that is not an Event's). It shows the Tenant and the Main Operator the Event has now (the Core's once it has started), and what it was configured with: `name`, `location`, `country`, `feiShowId`, `competitions`, `officials`, `operators`, `loops` and `combinations`. `GET /api/configure-events` lists the Setups of the Tenant the caller acts in for a Tenant Root or the Developer, and for anybody else those of the Events it runs now (a started Event is the Core's, so a hand-over moves its Setup from the list of the Main Operator who had it to the list of the one who has it), with the same `filter`, `sort` and `page[...]`.
- `PATCH /api/configure-events/{id}` changes the members it names, for the Main Operator, or the Developer, **before the Event starts**; from the start the Setup is not changed again (the Console works on the copies the Event made of it), and the answer is 409 `event-started` while it is Live and `event-ended` once it is Historic, whoever asks (403 `not-main-operator` for a person who could not have, whatever the stage). The Tenant and the Main Operator cannot be written (400 `unsupported-attribute`). A Setup the domain does not accept is 422 `invalid-attribute`. `DELETE /api/configure-events/{id}` removes an Event that has not started, with the grants the Main Operator gave on it: a Tenant Root of the Tenant or the Developer (403 `not-tenant-root`), and 409 `event-started` or `event-ended` after the start. `POST /api/configure-events` (above) takes the id the client made too: the same id again is that Event, 200.

### Searches across Tenants

- `GET /api/accounts?filter=contains(name,'text')` finds accounts by name among the members of the Tenant the caller acts in: the `account-matches` resource whose id is the account's, with a `displayName` and an `email` that is partly masked, at most ten, in the order of the names. A Tenant Root, a Main Operator of an Event of the Tenant that is not yet Historic, or the Developer (403 `not-allowed`). `GET /api/accounts/all-tenants` is the named view that reaches across Tenants, for the same people in any Tenant; no parameter turns the first into the second. Searches are limited per host (`Search:RateLimits`: `PerAccount` 30 and `Overall` 600 in a `Window` of ten minutes), and a request that is refused for what it asks, or because the caller may not, costs nothing: 429 `rate-limited` with `Retry-After`.
- `GET /api/athletes/all-tenants`, `/api/horses/all-tenants`, `/api/clubs/all-tenants` and `/api/officials/all-tenants` search the registries of every Tenant for any signed-in account (ADR-0010): the same filter, in which `name` stands for what names a row (its name, its English name and, for Athletes and Horses, its FEI ID), the same limits, and the same budget as the search of accounts. A match is a resource of the registry's type with the Tenant that owns the row (`tenantId`), `name`, `nameEnglish`, `feiId`, `club`, `country` and `role` where there are ones; nothing else of the row leaves, an Athlete's account included. An Official found in many Events is one match for each name and role. The Tenant's own list of a registry is a route of its family.

## Concurrency

- A Participation carries a `version` in the resource object's `meta`. A manual edit (PATCH) sends the version it was based on in `meta`; a stale one answers 409 `participation-changed` and a missing one 400 `version-required` (ADR-0013). Other resources (a profile, a record of session state) are last-write-wins.
- Creating a resource whose id the client mints (a Snapshot, ADR-0013) is idempotent: the same id again returns the first outcome. It never answers 409 for staleness.

## Legacy resources

Served by the Functions project, in their old shape (`Result<T>` envelope, PascalCase, HTTP 200 for domain errors): handouts, officials, operators (the Operators of an Event are grants), participations, rankings, settings, users (the profile of a user moved to `PATCH /api/me/profile`; user-sessions moved to the Api). The cross-tenant search of officials is served by the Api, and the family is not. The athletes, clubs, configure-event, countries, horses and event moved to the Api (above); the Functions project still answers their old routes until it is retired (#647), open as they always were, and nothing of the platform calls them. The routes of the event that went with a stored flag of its life (two lists and the verbs that started, ended and reset an Event) are gone: the Api starts and resets an Event, and an Event is over when its last day is. The ticket that ports a resource removes it from this list. Settings, the print routes and the routes that list users are not ported: they go with the Functions project (ADR-0011, ADR-0012, ADR-0013). Snapshot results are gone: what became of a Snapshot is the outcome of its time event on the Phase (ADR-0005).

## Done

An endpoint is done when every section above holds for it, every failure path returns a `code`, and an integration test covers one success and one rejected request.
