# REST API

Endpoints follow JSON:API 1.1 (jsonapi.org). Only the grammar of `filter` is borrowed from OData. The reasons are in ADR-0008.

## Routes

- A collection is a plural kebab-case noun: `/events`, `/user-sessions`. An item is `/events/{id}`.
- Event-scoped resources stay flat and carry `eventId` as an attribute: `/participations?filter=eventId eq 3f2504e0-4f89-41d3-9a0c-0305e82c3301`.
- A list of what an Event keeps (`participations`, `rankings`, `officials`, `handouts`) starts its filter with the Event, then `and` and whatever else (the Event may be in parentheses, which is how a client that joins its filters writes it). The Event says whose the rows are and which Tenant to read in (ADR-0012), so a list that does not start with one is 400 `event-required`, and no parameter names a Tenant. A row names its Event when it is made and keeps it: a change that names it is 400 `unsupported-attribute`, as is one that names the Tenant or the `version`.
- The method carries the meaning: POST creates (201, `Location`), GET reads, PATCH changes members (200 with the resource), DELETE removes (204).
- A named collection is a GET-only view of one resource type that the glossary names: `/events/live`, `/events/historic`. It returns the same resource type, each item's `self` link points at the canonical item URL, and it takes the same query parameters. Every other narrowing uses `filter`. The history of a Participant (`/participations/history`, below) is the one named view that tells its rows in a shape of its own, because each is composed with its Event and its Rankings.
- Model an operation as a create, update or delete of a resource: starting an Event is `POST /events` naming the configure event, resetting one is `DELETE /events/{id}`. An operation whose effect differs from its method's default meaning shows its intent in the path, `POST /{collection}/{id}/actions/{verb}`, and is noted in this file.

## Documents

- Media type `application/vnd.api+json` on both `Content-Type` and `Accept`.
- A resource object is `{ "type": "<collection>", "id": "<string>", "attributes": { ... } }`. The id is a string on the wire and a Guid in the domain (ADR-0009).
- Members are camelCase. Foreign keys are plain attributes (`eventId`, `participationId`). `relationships` and `include` wait for a consumer that needs them.
- Values the server computes (`isLive`) are read-only attributes; writes ignore them.

## Status and errors

- 200 read or update. 201 create. 202 taken, and the outcome is not told. 204 delete. 400 malformed request, filter or parameter. 401 not signed in. 403 not allowed. 404 missing item. 409 conflict with current state. 413 body of more than 1 MiB (`payload-too-large`). 422 domain rule violated. 429 too many requests (`rate-limited`, with the seconds to wait in `Retry-After`). 500 unexpected. An empty collection is 200 with `"data": []`.
- Every error is `{ "status", "code", "title", "detail"? }` in `errors`. `code` is a stable kebab-case identifier (`event-ended`) that clients branch on. `title` and `detail` are for people and change with the wording.
- The status always reports the outcome.

## Query parameters

- `filter` holds one OData `$filter` expression: `filter=eventId eq 3f2504e0-4f89-41d3-9a0c-0305e82c3301 and isNotRanked eq false`. A Guid is written unquoted, as the OData grammar has it, a string is quoted with its quotes doubled (`name eq 'O''Brien'`), and the members are the resource's in camelCase, a member of what a resource embeds by a path (`country/isoCode eq 'BG'`). The server maps the expression onto `ODataQueryOptions` and applies it to Mongo LINQ (`ReferenceQuery`). An expression that is not valid, or names a member the resource has not or keeps to itself, is 400 `invalid-filter`.
- `sort` lists members, `-` prefix for descending (`sort=-name,id`). It maps to `$orderby`; one that is not a list of members of the resource is 400 `invalid-sort`. A list that is not sorted is in the order of the ids, so that its pages do not overlap.
- `page[size]` (1 to 500, 100 when it is not named) and `page[number]` (from 1) cut a list into pages: 400 `invalid-page` for any other. The answer says which page it is in `meta.page` (`size`, `number`) and where the next one is in `links.next`, which is not there on the last. A collection that can outgrow one screen takes them.
- `fields[...]`, `include` and any other parameter answer 400 `unsupported-parameter` until a consumer needs them.
- A filter that is valid and that the data cannot run, or cannot run on a row (the date parts of a date, a division by zero, a part of a text that starts past its end), is 400 `invalid-filter` on every list, and never a 500, which is for what the caller did not cause. The page of every list is read in one place (`ReferencePages`), and the exception of a read that failed while it applied a caller's filter tells whose the failure is: the error of a part of the expression that has no row, and a command that the database refuses for the query (bad value, type mismatch, failed parse, overflow, failed conversion, the numbered assertions of its expressions), are the caller's; a lost connection, a time-out, rights and a command refused for the state of the server are the database's.
- The families of reference data take the whole grammar (the next section). `JsonApiQuery` still reads the part of it that the other routes use: members compared with `eq` and joined by `and`, for the members the route names. Any other expression, and any member the route does not name (the owner of a record, say), is 400 `invalid-filter`.
- A search is a list that starts from `filter=contains(name,'text')` (`JsonApiQuery.ReadSearch`) and is made by the database, never by reading rows and matching them in the Api. Every word of the text (six at most, 400 `invalid-filter` beyond) has to be part of one of the names of a row, in any order and in any case; a word is matched as it is written, a quote in it is doubled (`d''arcy`), and one of the words has at least two characters (400 `search-too-short`). The match is a regular expression that is not case-sensitive, built by the route (`NameSearch`), because OData's `contains` is case-sensitive and `tolower` lowers ASCII letters alone in MongoDB, so neither finds "иван" in "Иван". A search is not a listing of everybody, so one with no filter, another member or another expression is 400 `invalid-filter`, and so is a text with a null character. It takes `sort=name` or `sort=-name` (the ids follow where two names are the same, so that no row is twice or missing between two pages; any other sort is 400 `invalid-sort`) and the pages of every list, ten rows to a page unless `page[size]` says otherwise, twenty-five at most (400 `invalid-page`), with `meta.page` and `links.next`. A page is a search for the budget below. No route takes a parameter that names a Tenant or asks for every Tenant (`tenantId`, `allTenants` and the like are 400 `unsupported-parameter`, or ignored by a route that reads no parameters); what reaches across Tenants is a named view, below.

## Authorization

- Every route requires a signed-in caller unless it is on the public-read allowlist (ADR-0012): one list in the Api (`PublicEndpoints`), enumerated by a test (`DenyByDefaultTests` lists the real endpoints against it), read-only, and never a write. An unauthenticated caller gets 401 `not-signed-in`, never a redirect; a signed-in caller who may not do it gets 403 with a code such as `not-console-operator`. The rule is applied in one place, before any endpoint runs (`AccessBaseline`, `AccessBaselineMiddleware`): a route is public only because the list names it, and declaring it anonymous on the route does nothing, so a new route is protected until someone adds it to the list and to the test.
- The list has two kinds of entry. Public reads are views (`/healthz`, the Ui, the live hub and its negotiation, which only push what any viewer may see and have no method a client can call) and the answer to an unknown API route, a 404 for everybody. The sign-in surface (`/sign-in`, `/register`, `/privacy`, `/account/passkeys`, their assets, and the routes below that make a caller) is anonymous by nature.
- A write to a protected route sends the header `X-Requested-With: NoTiming`, or it is 400 `request-header-required`. A browser sends a header like that to another origin only after the origin has allowed it, which the CORS policy refuses, so another site (or a sibling subdomain, which SameSite does not keep out) cannot write with a visitor's cookie. The pages of the Api and the Ui send it on every write; a client that is not a page sends it too. The sign-in surface needs no header, because nobody is signed in yet.
- Repositories filter by the current Tenant by default (ADR-0012, #643). Every collection that a Tenant owns is read and written through `TenantCollection`, which joins every filter with the current Tenant, stamps what it writes and never moves a document from one Tenant to another; with no current Tenant a read finds nothing and a write is refused. The current Tenant is the Event's inside an Event, and elsewhere the Tenant the account has selected, or its home Tenant (`GET /api/me` says which). A cross-tenant read is a named view of its collection, never a parameter a caller can send to any resource; the ones there are: an Event by its id, the Events a Console Operator runs, `/api/{athletes,horses,clubs,officials}/all-tenants` and `/api/accounts/all-tenants`, the history of a Participant (`/api/participations/history` and the registry rows `/api/athletes/{id}/link` and `/api/horses/{id}/link` name, #638), and the public lists of Events (`/events/live`, `/events/historic`, with the Events resource). They are the only places that open such a collection without a Tenant (`CrossTenantReads`, `GrantInvitations`).
- What a caller may do is decided by one pure function of the domain (`AccessPolicy`, the access matrix of ADR-0012) over facts the server reads: the Level the caller holds at the place the action belongs to (Anonymous < Account < Staff < Console Operator < Root, per Event, Tenant or platform; Root is the Developer, or a Tenant Root in its own Tenant, and runs every Event of it at every stage the action allows), the state of that place (the stage of the Event, whether the Tenant is operational), and what the caller has been granted on the Event. It is asked in one place, the endpoint filter (`AccessFilter`), and by nothing else: a handler declares what it needs with `[Requires(Capability, PlaceIn)]`, says where the request names its place (the route, the body, the filter of a list, the row it changes, the Tenant the caller acts in) and takes the `AccessContext` the filter filled, with the caller, where they stand, and the Event or Tenant found once. A handler does not ask the policy, read the session or find its Event or Tenant itself. `GET /api/events/{id}/capabilities` asks the same policy for a screen, so what a screen offers and what the server accepts cannot differ. The policy answers with the reason that is missing, which the Api gives a status and a code derived from the Level the row needs: 401 `not-signed-in`; 403 `not-allowed` (Staff), `not-console-operator`, `not-root`, `not-developer` (Root at the platform); 409 `tenant-not-operational`, `event-not-started`, `event-started`, `event-ended`. The Level is checked before the stage of the Event, so a person who may not do it is only told that.
- A request is answered in one order, and the first thing wrong is the answer (ADR-0012, #671): signed in (401); the transport of the request (415 `unsupported-media-type`, 413 `payload-too-large`, 400 `malformed-request`, and the parameters of a list or a search); the place it names, found once (400 when it is named wrongly: `event-required` for a document that names no Event, or the empty one, `invalid-event` for a name that is not an id, `invalid-filter` for a list whose filter does not start with the Event, `invalid-id` for the Setup an Event starts from, 409 `no-current-tenant` for an account that acts in no Tenant where the action is done in one; 404 when it is not there, or is a row that is not); the Level the caller holds there (403) and then the stage (409); the content of the request, which validates itself by its type (400, 409 `id-mismatch`, 422), so that a person who may not do it is never told what is wrong with what they sent; and last the work, where the handler is reached with a caller who holds the Level and a request that is valid, and what the stored state refuses is answered (404 of a row that is not there, 409 `id-taken` or `participation-changed`, the rules of the domain as 422, which a handler throws as a typed exception and the Api maps in one place, `ApiFailures`). A request validates itself with `JsonApiBody<T>` (the document of a write, whose attributes say what is wrong with them in `IResourceAttributes.Invalid()` and what they say of their id), `ListQuery` (a list) and `SearchQuery` (a search by name); what can only be checked against the row a PATCH changes, and the version it names, is checked by the handler on the row it was handed, and the ceremony of the passkeys keeps the order of its protocol (the host supports passkeys, the antiforgery token is good, then the document).
- A route that is neither on the public list nor declares `[Requires]` stops the host from starting (`EndpointGuard`, which `RoutesOfTheApiTests` runs over the real routes), so a new route is protected until someone says what it needs; a route about a row of what an Event keeps or a Snapshot (`PlaceIn.EventOfRow`) says which rows with `IEventRows`. The jobs of the host (the finalisation of Rankings) are not routes and are not authorized: they check for themselves the stage they are for.
- There are no anonymous route groups. The sign-in routes below are the only writes that are anonymous: a person signs in to become a caller.
- A write sends `Content-Type: application/vnd.api+json`, and nothing else is read (415 `unsupported-media-type`). A browser may not send that type to another origin without a preflight, which the CORS policy refuses, so another site cannot write with a visitor's cookie. A body that is not one resource of the expected type is 400 `malformed-request`, and one of more than 1 MiB is 413 `payload-too-large`, before it is read.
- A record that belongs to a caller is found by owner only: a route names no owner, the store has no operation without one, and the record of another person is answered 404 `not-found`, exactly as a record that does not exist is.

## Authentication

A person signs in with a code sent by email or with a passkey, and the session is a cookie the server sets (ADR-0002). The cookie is `__Host-NoTiming`: host-only, HttpOnly, Secure, SameSite=Lax, persistent, 30 days sliding, and it carries only the key of a ticket the server keeps. The pages that use these routes are `/sign-in`, `/register`, `/privacy`, `/account/passkeys` and their assets, served by the Api; the Ui links to them.

- `POST /api/code-challenges` with `{ "email" }` asks for a code. It answers 202 with no body whether or not the address has an account, and inside the resend cooldown of the previous code, so the answer tells nothing; a malformed address is 400 `invalid-email`.
- `POST /api/registrations` with `{ "email", "givenName", "surname", "countryId", "website"? }` registers a new person (#601): 202 with no body, a code is mailed, and nothing is stored until the code comes back to `POST /api/sessions`, which then creates the account (confirmed address, the names, a home Tenant from the country, one membership in it) and signs it in. It answers alike for an address that has an account (that address is sent a sign-in code and what was typed is dropped), for one on a cooldown, for one a configured allow-list keeps from registering (`Registration:AllowList`: addresses and `@domain` entries; staging is closed without one, production is open without one) and for a body that fills `website`, the field of the page that people never see, which only a program fills in. A malformed address is 400 `invalid-email`, a missing, too long (100 characters) or control-character name 400 `invalid-name`, a country that is not one of those the page lists (it needs an ISO code) 400 `invalid-country`. The page lists the countries from the `countries` collection. Every 202 also sets `__Host-NoTiming-Registration` (HttpOnly, Secure, SameSite=Strict, 15 minutes, the same value for a browser that sends it back): its secret is hashed into the details that wait in the challenge, and they are used only when the code comes back with the same cookie. A code that comes back without it, from another browser, still proves the address and opens the account, without the names, the country and the home Tenant: whoever asked for a code for an address first cannot choose the account its owner gets.
- `POST /api/sessions` with `{ "email", "code" }` signs in: 201, the `sessions` resource `current` (`method`: `code` or `passkey`, and `passkeyCount`, which the sign-in page uses to decide whether to offer one) and the cookie. A wrong, spent, expired or exhausted code is 401 `invalid-code`, whatever the reason. With `{ "credential" }`, the assertion a passkey made as the browser's WebAuthn API serialises it, the same route signs in with a passkey; one that signs nobody in is 401 `invalid-passkey`, whatever the reason.
- Asking for a code (`/api/code-challenges` and `/api/registrations` alike) and trying one are rate limited, per host and per hour (`Auth:RateLimits`): a request draws on the budgets of its address (5), its client (10, a client being the forwarded address, an IPv6 one by its /64) and the platform (100); a wrong code draws on those of the address as that client tries it (5), the client (10) and the platform (100), and a right code costs nothing. A request that is out of a budget is 429 `rate-limited` with `Retry-After`, before the address is looked at, so it is the same for every address, and it costs nothing. A malformed request is not counted.
- `DELETE /api/sessions/current` signs out: 204, the ticket is deleted and the cookie cleared. Without a session it is 204 as well.
- `POST /api/dev/sessions` with `{ "email" }` (#607) signs in as an account on an allow-list, without a code, for a developer who runs the platform on their machine: 201, the `sessions` resource `current` with `method` `dev`, the `accountId` and the cookie. It exists in a Debug build of the Api and in no other (the code is compiled out of a Release build, so no deployed host has it), in the Development environment only, and only when `Dev:SignInAs:AllowList` (the user-secrets of the developer) names somebody; anywhere else it is the 404 of an unknown route. A request that is not from the machine itself (a loopback address, to `localhost`, `127.0.0.1` or `[::1]`, with no `X-Forwarded-*` or `Forwarded` header) is 403 `local-only`. The database has to say what it is, by the marker `mark-environment` (and `migrate-tenants --apply` and `seed-staging --apply`) writes, and the marker is read on every request: Production is 403 `production-database`, no marker, or a marker that says anything but Staging or Development, is 409 `environment-not-marked`. An address that is not on the allow-list is 403 `not-on-the-allow-list`, and one with no account is 404 `account-not-found`. The address stays as unconfirmed as it was and no invitation is taken. `GET /dev/sign-in-as` is its page, which lists the allow-list to the machine and to nobody else. Both are sign-in surface for a host that has them (`LocalhostPublicEndpoints`, in `Features/Localhost`) and are not on the list of the Api, which stays the one list of what a deployed host makes public.
- `GET /api/me` is the `accounts` resource of the caller (`email`, `emailConfirmed`, `name`, `passkeys`, `profileComplete`, `homeTenantId`, `selectedTenantId` and `currentTenantId` when there are ones, `memberships` (each `tenantId` and its `roles`) and `isDeveloper`), or 401 `not-signed-in`. A route that needs a caller answers 401 with that code, never a redirect. `PATCH /api/me` changes one member, `selectedTenantId`: the Tenant that what the caller reads and writes belongs to outside an Event, null to go back to the home Tenant. It has to be one the caller is a member of (the Developer may act in any Tenant that exists), or it is 422 `not-a-member`; any other member is 400 `unsupported-attribute`. No route gives a role or the Developer flag: `tenant-root` and `IsDeveloper` are written by the Developer's commands (`seed-tenant-root`, `grant-developer` in `tools/NTS.Tools`).
- `GET /api/me/profile` and `PATCH /api/me/profile` are the profile of the caller (#602), the `profiles` resource whose id is the account's: `givenName`, `middleName`, `surname`, `countryId` (the country its `countryRegion` names, when one of ours does), `countryRegion`, `club`, `feiId` and the computed `complete`. The routes name no account, so there is no way to reach another: a document that names an id that is not the caller's is 409 `profile-id-mismatch`. A PATCH names the members it changes: one that is not named stays, and an optional one that is null or blank is cleared. `givenName` and `surname` are required and `countryId` is the id of a country that has an ISO code; a value that is not valid (a name, club or FEI ID longer than 100, 100 and 20 characters, or with a control character, a country that cannot be chosen) is 400 `invalid-name`, `invalid-club`, `invalid-fei-id` or `invalid-country`, and a profile that would lack a country, a first name or a surname is 422 `profile-incomplete`; nothing is saved when either happens. The edit sets only the fields of the profile (the name is rebuilt from the three names): it never moves the home Tenant, though an account that has none is placed when it first picks a country.

### Passkeys

A passkey is a resource of the signed-in person: `/api/passkeys`, with its credential id in base64url as the id. They are discoverable, require user verification and are never attested; the relying-party ID is configuration (`Passkeys:RelyingPartyId`, `localhost` in Development), and a host with none answers 503 `passkeys-not-configured` on every route below that needs one.

- `POST /api/passkeys/actions/request-options` (anonymous) answers the options for `navigator.credentials.get`, and `POST /api/passkeys/actions/creation-options` (signed in) those for `navigator.credentials.create`, which exclude the passkeys the person has. Both are actions in the sense above: they create nothing, and they hold the challenge in a short-lived host-only cookie that the next call consumes.
- `POST /api/passkeys` with `{ "credential", "name"? }` stores the passkey the browser made: 201 and the resource, and a "new passkey added" email in the language of the request (a mail that cannot be sent is logged and does not undo the passkey). A credential that does not verify, or arrives with no ceremony underway, is 400 `invalid-passkey`.
- `GET /api/passkeys` lists them. `PATCH /api/passkeys/{id}` renames (`name`). A name is at most 60 characters, on both routes: longer is 400 `invalid-name`. `DELETE /api/passkeys/{id}` removes: 204, and the last passkey is 409 `last-passkey`, because losing the device would lock the person out. A passkey is looked up among the caller's own: someone else's, or none, is 404 `not-found`.
- The ceremony routes (the two actions, `POST /api/passkeys`, and `POST /api/sessions` with a credential) verify an antiforgery token on top of the media type: the header `X-XSRF-TOKEN` carries the token the server put into the page, and the cookie that goes with it is `__Host-NoTiming-Xsrf` (unprefixed and not Secure-only in Development, which runs on plain http). A request without a matching pair is 400 `antiforgery-token-invalid`.

### Session state

What a person keeps per Event (the Snapshots they have sent and the ones they have selected) is the `user-sessions` resource (#602), flat, with the Event as the attribute `eventId` and the state as the member `state` (`snapshotHistory`: groups of `entries`, a `type` and the `groupId` they were sent under, and `snapshotSelections`; an entry has `number`, `name`, `timestamp` (the time of the day) and `time` (the instant, with its date); a group or an entry kept before them has neither; enums are their names). It is the caller's own: the routes name no owner, the store finds records by owner only, and a record of another person is 404 `not-found`, exactly as one that does not exist is.

- `GET /api/user-sessions` lists the caller's records and takes the filter `eventId eq <id>`, `sort=eventId` or `sort=-eventId` (the ids follow, so that no record is twice or missing between two pages) and the pages of every list, `page[size]` and `page[number]` with `meta.page` and `links.next`; the owner cannot be named in it (400 `invalid-filter`), another member to sort by is 400 `invalid-sort`, and `fields`, `include` and any other parameter are 400 `unsupported-parameter`. `GET /api/user-sessions/{id}` reads one.
- `POST /api/user-sessions` with `{ "eventId", "state"? }` makes the caller's record for the Event, or returns the one they have: 201 with `Location` the first time and 200 after, and a state offered to a record that exists is not put over it. The id is the server's: a document that brings one is 403 `client-id-not-supported`, and an Event id that is not one is 400 `invalid-event`.
- `PATCH /api/user-sessions/{id}` replaces `state`. The Event of a record does not change: naming another is 409 `event-immutable`. `DELETE /api/user-sessions/{id}` removes the record: 204.
- What is stored is what the Functions API stored (PascalCase members, enums as text, no null member, the constant Tenant `nts` until the Tenants of ADR-0012 reach the data), so the records that exist read the same; the owner is the account id. The routes of the Functions API that listed or read by a user identifier, which let anyone read anyone's, have no equivalent (below).

### Tenants

- `GET /api/tenants/{id}` is the `tenants` resource, whose id is the key of its kind and country (`country-bg`, a text and not a Guid): `name`, `kind`, `isOperational` (it has a Tenant Root, which the Developer's command gives) and `regionalRules` (`onlyAverageLoopSpeed`, and `rankerCode` when there is one), for any signed-in caller; an unknown Tenant is 404. `PATCH /api/tenants/{id}` edits the rules, which an Event copies when it starts and never reads from the Tenant again: Root of the Tenant, a Tenant Root of it or the Developer (403 `not-root` for anybody else); a document that names another id than the route's is 409 `tenant-id-mismatch`. The members it names are merged into the rules (not named stays, a null `rankerCode` clears it), rules that are not valid are 400 `invalid-rules`, and a member of the Tenant other than `regionalRules` is 400 `unsupported-attribute`.
- `GET /api/tenants/{id}/capabilities` is the `capabilities` resource of the Tenant for the caller (`level`, what the caller is in the Tenant, `canCreateEvents`, `canEditTenant` and `canEditRegistry`), from the same policy.

### Branding

The logos at the head of what an Event prints (#646, ADR-0012). The `brandings` resource has a Tenant's and an Event's, with no id of its own: its id is the Tenant's or the Event's, and its members are the logos of the two positions, `left` and `right`. A logo is `{ contentType, content, size }`, with the image as base64 in `content` (JSON:API has no body but a document), `contentType` one of `image/png`, `image/jpeg`, `image/gif` and `image/webp`, and `size` the weight of the image in bytes, which is read-only. A position that has no logo is not in the document.

- `GET /api/tenants/{id}/branding` is the Tenant's own logos, and `PATCH` changes them: Root of the Tenant (403 `not-root` for anybody else, on the read too); an unknown Tenant is 404. A PATCH names the positions it changes: a logo sets the position, `null` clears it, and one that is not named stays; any other member is 400 `unsupported-attribute`. The answer is the Tenant's logos as they are after it.
- `GET /api/events/{id}/branding` is what the Event is printed with, for any signed-in caller: for each position the Event's own logo, with `source: "event"`, and where it has none the Tenant's, with `source: "tenant"`, and none where neither has one. `PATCH` changes the Event's own logos, the same way, and the answer is what it is printed with after it: a Console Operator of the Event, or Root (403 `not-console-operator`), while the Event has not ended (409 `event-ended`, which is the policy's row of `ConfigureEvent`). An Event that is not there, or an id that is not one, is 404. An Event's logos are not touched by a reset, and go with the Event when it is deleted before it started.
- A logo that is not one is 400 `invalid-logo` (not an object with a `contentType` and a `content` and nothing else, a kind that is not printed, content that is not base64 or that does not begin as an image of the kind it names does) and one that weighs more than 512 KiB is 422 `logo-too-large`; nothing of the request is kept when any of it is refused, so a request that sets one position and names an invalid one for the other changes neither. A document is read whole before it is looked at, so two logos of 512 KiB in one request are more than the 1 MiB a request may hold (413 `payload-too-large`): a client sends them one at a time.

### Events and who runs them

An Event belongs to one Tenant (ADR-0012), a field of its document, the Setup's before it starts and the Core's after, which travels with it when it starts. Root, a Tenant Root of that Tenant or the Developer, runs it at every stage; beside Root the people who run it are its Console Operators, grants of the Event that Root assigns (below), and the Officials and Operators that a Console Operator links are its Staff. Whether it is Live is a rule of its end and the clock of the host (`EventStageRule`, ADR-0007), never a stored flag; the stage is `unstarted`, `live` or `historic`.

- `POST /api/configure-events` with `{ "name", "location" }` and any other member a change of a Setup may name (`feiShowId`, `country`, `competitions`, `officials`, `operators`, `loops`, `combinations`) makes an Event in the Tenant the caller acts in: 201, its `Location` and the `configure-events` resource as it is read. The document may name the id of the Event (`data.id`, a Guid), as a client that makes its ids does; the same id again is that Event, 200, and an id that another Tenant's Event has is 409 `id-taken`. A Tenant Root of that Tenant, or the Developer (403 `not-tenant-root`); the Tenant has to be operational (409 `tenant-not-operational`, the Developer included) and its country has to be among the countries (409 `tenant-country-missing`); with no current Tenant it is 409 `no-current-tenant`. A name or location that is blank, longer than 100 characters or of more than one line is 400 `invalid-name` or `invalid-location`. The Event cannot be given a Tenant, or a member a Setup has not: that is 400 `unsupported-attribute`. A member that is not named is what a new Setup has, nothing configured and the country of the Tenant. A Setup the domain does not accept is 422 `invalid-attribute` and none is made. The read of it, and its changes, are the Setup's own routes.
- `POST /api/console-operators` with `{ "eventId", "email" | "accountId" }` assigns a Console Operator to an Event, `GET /api/console-operators?filter=eventId eq <id>` lists them and `DELETE /api/console-operators/{id}` removes one: 204. They are grants of their own resource, so that every route carries one fixed requirement: only Root assigns and removes (403 `not-root`; a caller who may not read the Console Operators of the Event is told 404 on a removal, as for one that does not exist), while the Event has not ended (409 `event-ended`), and Root and the Console Operators of the Event list them whatever the stage (403 `not-console-operator` for anybody else; the pages and `sort=email` of every list). The person is named by an email (400 `invalid-email`) or by an account (422 `account-not-found`), and by one of them (400 `malformed-request`); an email that has an account gives it the grant at once, and one that has none is a pending invitation (`pending: true`) that gives nothing and attaches when that person registers or signs in with a code to it; the same person is one grant, 201 and then 200. A grant's attributes are `eventId`, `pending`, `accountId` and `displayName` when there is an account, and an `email` that is partly masked.
- `GET /api/events/{id}/capabilities` is the `capabilities` resource of the Event for the caller: `stage`, `level` (what the caller is at the Event: `anonymous`, `account`, `staff`, `consoleOperator` or `root`), `canSnapshot`, `canCreateEvents` (in the Event's Tenant) and what the Console offers (#646): `canConfigure` (start, change, brand it and link its Officials and Operators), `canEditSetup`, `canRun` (edit what it keeps, and reset it) and `canAssignConsoleOperators`. It is the policy's own answer for the caller and the Event as they are now, so what a screen offers and what the server accepts cannot differ. An Event that is not there, or an id that is not one, is 404.

### Grants

A Console Operator of an Event, or Root, links people to the Officials and Operators of the Event: the `event-grants` resource, flat, with the Event as the attribute `eventId` (ADR-0012). A grant is in the Tenant of its Event and gives Snapshot access to an Operator, and to an Official of a role that may (Steward, ChiefSteward, GroundJury, GroundJuryPresident); any Official is Staff and sees how times were recorded.

- `POST /api/event-grants` with `{ "eventId", "kind", "officialRole"?, "email" | "accountId" }`: `kind` is `operator` or `official` (400 `invalid-kind`: never a role of the Tenant or of the platform), `officialRole` is a role of the domain by its name for an Official and none for an Operator (400 `invalid-role`), and the person is named by an email (400 `invalid-email`) or by an account (422 `account-not-found`) and by one of them. 201 and the grant, or 200 and the one that was made before: the same person in the same kind and role is one grant. An email that has an account gives it the grant at once; one that has none is a pending invitation (`pending: true`), which gives nothing and attaches to the account that registers with that email, or signs in with a code to it. A Console Operator of the Event, or Root (403 `not-console-operator`), while the Event has not ended (409 `event-ended`); 404 for an Event that is not there. An Event holds at most 500 grants: one more is 422 `grant-limit-reached`, though a grant it has is still answered with 200. Attaching a pending invitation to the account that signs in never fails the sign-in: when the grants cannot be written it is logged and tried again at the next sign-in.
- `GET /api/event-grants?filter=eventId eq <id>` lists the grants of one Event for a Console Operator of it or Root, whatever the stage, the Console Operators not among them (they are `console-operators`); there is no listing without the Event. It takes `sort=email` or `sort=-email` (the ids follow) and the pages of every list (`page[size]`, `page[number]`, `meta.page`, `links.next`; 400 `invalid-sort`, `invalid-page`), and the database makes them. `DELETE /api/event-grants/{id}` removes one, and the access ends with it: 204, and to anybody who is not a Console Operator of its Event, or Root, it is 404, as it is for one that does not exist. A grant's attributes are `eventId`, `kind`, `officialRole`, `pending`, `accountId` and `displayName` when there is an account, and an `email` that is partly masked (`a***@example.test`): an address never comes back whole.

### The Event

An Event is the `events` resource once it has started (#628, ADR-0007). Until then it is a Setup (`configure-events`), which is not an Event: it is not found here.

- `GET /api/events`, `GET /api/events/live`, `GET /api/events/historic` and `GET /api/events/{id}` are public reads of the Events that have started, of every Tenant (they are on the public list of ADR-0012, and read-only). The two named collections split the Events by the clock of the host, return the same `events` resources, link each item's `self` to `/api/events/{id}`, and take the parameters of every list (`filter` over the members of the Event, `sort`, `page[...]`); an expression that is valid but that the data cannot run, such as `year(endDay)`, is 400 `invalid-filter`. An id that is not an Event's, or is a Setup's, is 404.
- An Event shows `name`, `location`, `country`, `feiShowId`, `startDay`, `endDay`, `tenantId`, `regionalRules` (the rules of the Tenant when it started) and the read-only `isLive`, which is `true` until the end of its last day and `false` from the second `endDay` names, with no grace, and is told by the clock and never stored. Who runs it is not shown.
- `POST /api/events` starts an Event from its Setup. The document names the Setup as the id of the resource and takes nothing else: `{ "data": { "type": "events", "id": "<the id of the Setup>", "attributes": {} } }` (400 `id-required`, `invalid-id`, `unsupported-attribute`; 404 for a Setup that is not there). It is 201, its `Location` and the resource, or 200 and the Event that was started when the same Setup is started again. It is a Console Operator's of the Event and Root's, which is the policy row of configuring an Event (403 `not-console-operator`; 409 `event-ended` for an Event that is over; 409 `tenant-not-found` for a Setup whose Tenant is gone). The Event keeps the Tenant of its Setup and the rules of its Tenant as they are then, copies the Officials and the Operators, and creates the Participations and the Rankings of its competitions. A Setup that is not whole is 422 `invalid-setup`, one that configures the FEI export in part is 422 `incomplete-fei-configuration`, each with what is missing in `detail`, and one an Event cannot be made of is 422 `invalid-attribute`. A start that fails leaves no Event behind.
- `PATCH /api/events/{id}` changes the members it names (`name`, `location`, `country`, `feiShowId`, `startDay`, `endDay`; null takes a member away) for a Console Operator of the Event and Root, while the Event is Live (403 `not-console-operator`; 409 `event-ended`; an Event that has not started is 404). The days are whole days in the offset they are given in, and an Event is over when its last day is, so changing its days cannot end it, and cannot make it start after its last day (422 `invalid-attribute`). Its Tenant and its rules are not written (400 `unsupported-attribute`).
- `DELETE /api/events/{id}` resets an Event to its Setup, for a Console Operator of the Event and Root, while the Event is Live (403 `not-console-operator`; 409 `event-not-started` or `event-ended`). It removes what the Event made, what was kept for it (the state of a person) and the Event itself, last, so that a reset that stopped is made again by making it again: 204.

### Reference data and the Setup

The Clubs, Horses and Athletes of a Tenant's registry, the countries of the platform and the Setup of an Event move as JSON:API resources (#603, ADR-0008): `clubs`, `horses`, `athletes`, `countries` and `configure-events`. The routes of the first four are the same (`ReferenceEndpoints`), over a model of the domain whose members are the attributes, in camelCase, nulls left out, with the id as the resource's own. The client reads and writes them through the JSON:API variant of its repository (`JsonApiRepository`, `JsonApiClient`), which pages through a list, writes a member that is null as null (on a change it is a member taken away), and reads an error with its `code` (`LastError`).

- `GET /api/{type}` lists, with `filter`, `sort` and `page[...]` above; `GET /api/{type}/{id}` reads. Any signed-in account reads, the rows of the Tenant it acts in: a row of another Tenant, a missing one and an id that is not a Guid are alike 404 `not-found`, and an account with no current Tenant lists nothing. The countries are the platform's, so every account reads all of them. Nobody who is not signed in reads any (401).
- `POST /api/{type}` makes a row and answers 201 with the resource and its `Location`. The document may name the id (`data.id`, a Guid), as a client that makes its ids does: the same id again is the row that was made, 200 and the first outcome, and an id that another Tenant's row has is 409 `id-taken`; with no id the server makes one. Members the server owns (`tenantId`) or keeps to itself, and members the resource has not, are 400 `unsupported-attribute` and nothing is written; a member of another type is 400 `malformed-request`; a row the domain does not accept (a blank name, an Athlete with no Country, a FEI ID that is not a number) is 422 `invalid-attribute` with the member in `detail`.
- `PATCH /api/{type}/{id}` changes the members the document names and no others (200 and the resource); a member sent as null is taken away. A document that names another id is 409 `id-mismatch`. `DELETE /api/{type}/{id}` removes (204), and a row that is not there, or is another Tenant's, is 404. An Athlete or a Horse that a Participation refers to is not removed (#635, ADR-0010): the copies a Participation keeps carry the id of their row, so a row that is named by a Participation of any Tenant, of an Event that has started or of one that has not, is 409 `athlete-in-use` or `horse-in-use`; the row is found among the Tenant's own first, so another Tenant's row is 404 whether it is named or not. The countries are not removed: there is no route, because Events and Athletes embed one.
- Who writes: Root of the Tenant and a Console Operator of an Event of it that is not yet Historic, for Clubs, Horses and Athletes (403 `not-console-operator`; the policy's `EditRegistry`, asked in the Tenant the account acts in, so that an account with no current Tenant cannot write a registry: 409 `no-current-tenant`); the Developer alone for the countries (403 `not-developer`). The Level is asked before the document is looked at and before the row is looked for.
- An Athlete embeds its `country` and its `club`, which can be filtered on (`country/isoCode`). An Athlete is linked to no account (#635, ADR-0010): a stored document that still holds the old link (`user`, with an email and more) is read without it, no route shows it or takes it (a document that names `user` is 400 `unsupported-attribute`, and it is not in the grammar of `filter` or `sort`), so no route says which account a rider was linked to and no filter finds a rider by an address, and an edit of an Athlete leaves the stored link as it was.
- `GET /api/configure-events/{id}` reads the Setup of an Event: a Console Operator of the Event and Root, at any stage (403 `not-console-operator` for anybody else, 404 for an id that is not an Event's). It shows the Tenant the Event is in, and what it was configured with: `name`, `location`, `country`, `feiShowId`, `competitions`, `officials`, `operators`, `loops` and `combinations`. `GET /api/configure-events` lists the Setups of the Tenant the caller acts in for Root, and for anybody else those of the Events it is a Console Operator of, with the same `filter`, `sort` and `page[...]`.
- `PATCH /api/configure-events/{id}` changes the members it names, for a Console Operator of the Event, or Root, **before the Event starts**; from the start the Setup is not changed again (the Console works on the copies the Event made of it), and the answer is 409 `event-started` while it is Live and `event-ended` once it is Historic, to a person who could have changed it (403 `not-console-operator` for a person who could not have, whatever the stage). The Tenant cannot be written (400 `unsupported-attribute`). A Setup the domain does not accept is 422 `invalid-attribute`. `DELETE /api/configure-events/{id}` removes an Event that has not started, with the grants given on it: Root (403 `not-root`), and 409 `event-started` or `event-ended` after the start. `POST /api/configure-events` (above) takes the id the client made too: the same id again is that Event, 200.

### What an Event keeps

The Participations, Rankings, Officials and Handouts an Event made when it started move as JSON:API resources (#604, ADR-0006, ADR-0008, ADR-0012, ADR-0013): `participations`, `rankings`, `officials` and `handouts`, flat, with the Event as the attribute `eventId`. The routes of the four are the same (`EventDataEndpoints`), over the model of the domain whose members are the attributes. The client reads and writes them through the JSON:API variant of its repository, scoped to the Event the Ui has selected, which puts the Event at the head of every list it asks for.

- `GET /api/{type}?filter=eventId eq <id> and ...` lists the rows of one Event, with `sort` and `page[...]`, and `GET /api/{type}/{id}` reads one. Anybody reads, signed in or not (ADR-0001): they are what the public views of the Event show, but for a list of Participations that is cut by the Athlete or the Horse of their Combination, which is for a signed-in account (#638, below). A list names its Event (400 `event-required`) and takes no Tenant (400 `unsupported-parameter`): the Tenant of a row is the Tenant of its Event. The list of an Event that is not there is empty, and a row is found by its id whatever the Tenant, or is 404. What the resource keeps to the server is not shown, taken or filterable: the bookkeeping of the documents the Functions API wrote (`isDeleted`, `deletedVersion`), the version of a Participation, which is told in the `meta` of each resource (`"meta": { "version": 3 }`) and is no attribute, and the account an Official is linked to.
- **A Participation tells how its times were recorded only to Staff** (#619, ADR-0005, ADR-0012): every Phase tells the times it shows (`arriveTime`, `presentTime`, `representTime`, left out when it shows none), and tells its `events` to a caller who may see how times were recorded (the policy's `SeeTimeEvents`, asked with the grants read on the request): an Official or an Operator linked to the Event, its Console Operators, and Root. Each event has `kind` (`Arrived`, `Presented`, `ArriveUpdated`, `PresentUpdated`, and `PhaseUpdated`, an edit of the Phase form by a Console Operator or Root), `time` (a `PhaseUpdated` has none: it lists its times in `changes`, each with the `slot`, `Arrive`, `Present` or `Represent`, and its `time`, left out when the edit cleared that time, which is a time that is listed and has none), `isRepresent`, `outcome`, `method`, `recordedAt`, `actorId`, and `disabledAt` when a Console Operator or Root disabled it (its `outcome` is then `RejectedManually`). Anybody else, a visitor and a signed-in account that is not Staff of the Event alike, reads `events` as an empty list, on the same URL. What a write answers is the Participation as Staff read it. A client makes a Phase from its events when it has them, and from the times when it has none.
- `GET /api/time-event-actors?filter=eventId eq <id>` names the people who recorded the times of the Event (#619): one resource of the type `time-event-actors` for each account that is the `actorId` of a time event of a Participation of the Event, with the id of the account as its id and `displayName` as its attribute (an account that is gone is not named, and an Event whose times nobody recorded has an empty list). It is for the callers who may see how times were recorded: 401 for a visitor, 403 `not-allowed` for anybody else, 404 for an Event that is not there; it takes the Event at the head of its filter, `sort=displayName` or `sort=-displayName` (the ids follow) and the pages of every list, and nothing else (400 `invalid-filter`, which is also a filter that does not name the Event, `invalid-sort`, `invalid-page`, `unsupported-parameter`; all of them before the caller is asked).
- `POST /api/{type}` makes a row, and answers 201 with the resource and its `Location`. The document names the Event (`eventId`: 400 `event-required` without it, 400 `invalid-event` when it is not an id, 404 when there is none) and may name the id (400 `invalid-id`), as a client that makes its ids does: the same id again is the row that was made, 200, and an id that a row of another Event or Tenant has is 409 `id-taken`. A row the domain does not accept is 422 `invalid-attribute`. Members the server owns or keeps to itself, and members the resource has not, are 400 `unsupported-attribute`.
- `PATCH /api/{type}/{id}` changes the members the document names and no others (200 and the resource): the Event, the Tenant and the version are not among them. The document of a Participation names the version it was based on in its `meta` and the row is then at the next one: a document without one is 400 `version-required`, one that is not a whole number from 0 is 400 `malformed-request`, and one that was made on another version is 409 `participation-changed` and changes nothing, whatever it names. Of two changes made at one version only one is taken. A change that names nothing changes nothing. Rankings, Officials and Handouts count no writes: the last change is the one that stays. `DELETE /api/{type}/{id}` removes the row (204), but not a Participation that a Ranking still counts or that a Handout is of: that is 409 `participation-in-use`, because what they show could not be composed without it (ADR-0006), and the Console takes it out of the Rankings and removes its Handouts first.
- Who writes: a Console Operator of the Event and Root, while the Event is Live (the policy's `RunEvent`: 403 `not-console-operator`; 409 `event-not-started` for a Setup, which has none of these, and 409 `event-ended`). The Event is the one the document of a new row names, and the one the row belongs to for a change or a removal, which is found by the id of the row once and handed to the handler, so that nobody is let in to one Event and writes another's row. What is written is the Tenant's of the Event, and a row that is in another Tenant than its Event is not written through it.
- A write that was stored is announced to the clients of the Event once (`ParticipationChanged`, for a Participation that is made, changed or removed), and one that was not stored, or changed nothing, is not.

### Snapshots

The times of a ride are recorded by the server (#644, ADR-0013, ADR-0005): the Snapshot an Official captured is a request, and the answer is the time event it was recorded as. The resource is `snapshots`, and nothing else records a time.

- `POST /api/snapshots` sends one: `{ "data": { "type": "snapshots", "id": "<guid>", "attributes": { "eventId", "number", "kind", "time" } } }`. The id is a Guid the device made, and is the id of the time event and the key of a Snapshot sent again (400 `id-required`, 400 `invalid-id`). `number` is the start number, `kind` is `Arrive`, `Present` or `Final` and `time` the instant it was captured, with its offset (400 `invalid-snapshot`; 400 `event-required` without the Event, 400 `invalid-event` when it is not an id). Who sent it and when it was recorded are the server's to say: a member that is not one of these is 400 `unsupported-attribute`.
- The answer is **201** with the resource and its `Location` whatever the outcome, because the event is what was made, and the outcome is a member of it: `eventId`, `participationId`, `number`, `slot` (`Arrive`, `Present` or `Represent`: the time of the Phase it feeds), `time`, `outcome` (`Accepted`, or `RejectedDuplicateArrive`, `RejectedDuplicatePresent`, `RejectedParticipationComplete`, `RejectedSeparateStageLine`, `RejectedSeparateFinishLine`, `RejectedInvalidTime`), `phaseId`, `gate` and `recordedAt`. The same id again is **200** with the first answer and writes nothing, and the id of a Snapshot of another Participation, or of an edit of the Phase form, which is no Snapshot, is 409 `id-taken`. An Event or a start number that is not there is 404 `not-found` or `participation-not-found`.
- Who may is asked of the policy (`SendSnapshot`) on every request by the endpoint filter, with the grants read on it, so that a person whose access was removed is refused on the next one: the Operators and the Officials of a role that may record, the Console Operators of the Event and Root (a Tenant Root of its Tenant and the Developer included): 401 not signed in, 403 `not-allowed`, and 409 `event-not-started` or `event-ended` for an Event that is not Live. It is asked before the document is looked at, so a person who may not send one is not told what is wrong with it. A Participation that is written by more at once than the server will wait for is 409 `participation-busy`: send it again.
- `POST /api/snapshots/actions/send-group` sends a list to one Event, `{ "data": [ resource, ... ] }`, at most 100, in order, and none stops the ones after it. The Event of the group is the one the first Snapshot that names an Event gives, so that the caller is asked once, before the handler; a Snapshot of the group that is of another Event is that entry's 409 `event-mismatch`. It answers **200** with `{ "meta": { "results": [ { "status", "data" or "errors" }, ... ] } }`: a result for each entry, in its order, with the status and the document that entry would have had alone. A body that is not a list is 400 `malformed-request`, and one with too many entries 400 `too-many-snapshots`, after the caller has been asked.
- `PATCH /api/snapshots/{id}` is an Update of a Snapshot that was sent: `{ "data": { "type": "snapshots", "id": "<id>", "attributes": { "time" } } }`, the time it should have had, an absolute value, so the last write wins and a replay is harmless. It is an event of its own, on the Phase the new time belongs to, and the answer is **200** with the attributes of that event and `previousTime` and `currentTime`, the times the Phase showed for that slot before and shows now (the same when it was rejected). A Snapshot that is not there is 404 `not-found`, so is the id of an edit of the Phase form; the Participation that holds it says which Event it is of, and the caller is asked of the policy for that Event like for a Snapshot.
- Every write that was stored, a rejected event too, is announced to the clients of the Event once (`ParticipationChanged`), and nobody has to be connected for a time to be recorded.

### Searches across Tenants

- `GET /api/accounts?filter=contains(name,'text')` finds accounts by name among the members of the Tenant the caller acts in: the `account-matches` resource whose id is the account's, with a `displayName` and an `email` that is partly masked, in the order of the names, a page of ten unless it is asked to be another size (`sort` and `page[...]` as every search takes them). Root of the Tenant, or a Console Operator of an Event of the Tenant that is not yet Historic (403 `not-console-operator`; the policy's `EditRegistry`); an account that acts in no Tenant is asked what the platform asks (`SetUpAcrossTenants`) and finds nobody in it. `GET /api/accounts/all-tenants` is the named view that reaches across Tenants, for the people who set an Event up in any Tenant (`SetUpAcrossTenants`: a Console Operator of an Event that is not yet Historic, a Tenant Root and the Developer); no parameter turns the first into the second. A request is answered in this order: the query (400), who is asking (403), the length of the words (400 `search-too-short`), and the budget (429). Searches are limited per host (`Search:RateLimits`: `PerAccount` 30 and `Overall` 600 in a `Window` of ten minutes), and a request that is refused for what it asks, or because the caller may not, costs nothing: 429 `rate-limited` with `Retry-After`.
- `GET /api/athletes/all-tenants`, `/api/horses/all-tenants`, `/api/clubs/all-tenants` and `/api/officials/all-tenants` search the registries of every Tenant for any signed-in account (ADR-0010): the same filter, in which `name` stands for what names a row (its name, its English name and, for Athletes and Horses, its FEI ID, which is matched only for the people who set an Event up: below), the same sort and pages, the same limits, and the same budget as the search of accounts. A name is found in the script it is registered in and in English where the row has its name in English; there is no tolerance of another spelling of the same letters (ADR-0010). A match is a resource of the registry's type with the Tenant that owns the row (`tenantId`), `name`, `nameEnglish`, `feiId`, `club`, `country` and `role` where there are ones; nothing else of the row leaves, an Athlete's account included. **An Athlete or a Horse is `name` and `nameEnglish` and nothing else to every signed-in account** (the owner's rule of 2026-10-23: no more of a person than the name), and the whole row (`tenantId`, `feiId`, `club`, `country`) only to the people who set an Event up (`SetUpAcrossTenants`: a Console Operator of an Event that is not yet Historic, a Tenant Root and the Developer), which are also the only callers whose words are matched against the FEI ID: a search for a FEI ID by anybody else finds nothing. A future member of a person (a profile) joins the whole row and is never added to the name. An Official found in many Events is one match for each name and role. The Tenant's own list of a registry is a route of its family.

### The history of a Participant

What an Athlete or a Horse (a Participant, see CONTEXT.md) has ridden, wherever, is read through the routes below (#638, ADR-0010, ADR-0006). They are for signed-in accounts alone (401 `not-signed-in`), and they reach across Tenants through named reads (`CrossTenantReads`): a ride names the registry row of its Athlete and of its Horse by id, whatever Tenant ran it.

- `GET /api/participations/history?filter=athleteId eq <id> and ...`, or `horseId eq <id>`, is the history of an Athlete or a Horse: a named view of the Participations that tells each ride in a shape of its own, one `participation-histories` resource for each Participation, in any Tenant, of an Event that has ended (a Live Event has no line yet; a Participation that the Functions API flagged as deleted is not one), newest first, with `sort` and `page[...]` above, and the `self` link of each at the Participation itself (`/api/participations/{id}`, which stays public). The filter starts with the Participant it is of (400 `subject-required`) and may go on with `and` and the members of a ride, `eventId`, `eventName`, `location`, `startDay`, `endDay`, `competition`, `ruleset`, `category`, `athleteId` and `horseId`; `other`, `placing` and `alsoCountedIn` are kept from `filter` and `sort`. The database joins the rides with their Events, filters, sorts and cuts the page (the id of the ride follows the sort, so that no ride is twice or missing between two pages), and a line is composed for the rides of the page from the Participation, its Event and the Rankings that count it (ADR-0006); the rides are read for the Participant named first: nothing that follows widens the list to another's.
- A line has `other`, the other half of the Combination (the Horse of an Athlete's ride, the Athlete of a Horse's), with `kind`, `id` and `displayName` as above, in English for a FEI Competition whatever the language. `placing` is what the ride placed as in the Ranking of its own Competition and Category, the one that carries the name, the ruleset and the Category of the ride: `{ "kind": "Ranked", "rank" }` is the rank that Ranking stores once the Event is Historic, the rank the Results give while it holds none, and 1 for its only entry; `{ "kind": "Eliminated", "code" }` has the code the Results show (`WD`, `FTQ GA`, `DQ ...`); `{ "kind": "NotRanked" }` stands for an entry marked not ranked. It is left out when the ride has no such Ranking, or the Ranking cannot be ranked, and the line is listed all the same. `alsoCountedIn` lists the other Rankings that count the ride, by name, Category and id, with `rankingId`, `name`, `ruleset`, `category` and the `placing` the ride has in each.
- `POST /api/athletes/{id}/link` links the caller as that Athlete (a bookmark, not a claim: nothing is granted by it), and `POST /api/horses/{id}/link` adds that Horse to the caller's Horses, at most a hundred (422 `horse-limit-reached`). The answer is a `participant-links` resource whose id is the Participant's, with `kind` and `displayName`: 201 with its `Location` when the link was made, 200 when the caller had it already. A caller is one Athlete at a time, so linking another moves the link. `GET` on the same route reads the link of the caller, and `DELETE` takes it away (204); a Participant the caller is not linked to, and a row that is not in the registry of any Tenant, are alike 404 `not-found` (a link to a row that has been deleted since can still be taken away). The routes name no account, so there is no way to reach the links of another person, and they are the only way to make or take away a link. What a person is linked to is told by their profile, `GET /api/me/profile`: read only `athlete` (`kind`, `id`, `displayName`, left out when there is none) and `horses` (a list of the same, in the order they were added), the names in the language of the request; a link to a row that has been deleted since is not shown, and can still be taken away.
- A look-up of a Participant in what an Event keeps is for signed-in accounts as well: a list of `participations` whose filter names the Athlete or the Horse of the Combination (`combination/athlete/...`, `combination/horse/...`) is 401 `not-signed-in` for a visitor, though the rest of that list, the Event's own, is public. The Participations are indexed by the id of the Athlete and by the id of the Horse they copy.
- The language of a request is its `Accept-Language`: the first of `en` and `bg` it names, English when it names none. The routes above take no `lang` parameter (that is the sign-in pages', and is 400 `unsupported-parameter` here), so the Ui sends the language the app is in on every request, which is not always the browser's.

## Concurrency

- A Participation carries a `version` in the resource object's `meta`. A manual edit (PATCH) sends the version it was based on in `meta`; a stale one answers 409 `participation-changed` and a missing one 400 `version-required` (ADR-0013). Other resources (a profile, a record of session state) are last-write-wins.
- Creating a resource whose id the client mints (a Snapshot, ADR-0013) is idempotent: the same id again returns the first outcome. It never answers 409 for staleness: the server writes a Snapshot or an Update of one against the version of the Participation and, when another write got there first, reads the Participation again and places the time again, so that both are recorded and the version counts each.

## Routes that were not ported

The Functions API retired with #647 (ADR-0011). The resources of it that the platform still needs are served by the Api, in the shape the routes above describe and not the old one (the `Result<T>` envelope, PascalCase members, HTTP 200 for a domain error). These routes have no equivalent, on purpose (#604, #647):

- **Registration and the profile by email** (`POST users/register`, `GET users/{email}`, `PATCH users/{email}/profile`): a person registers with an emailed code and keeps their own profile (`POST /api/registrations`, `GET` and `PATCH /api/me/profile`), so nobody reads or writes another's by an address.
- **User listings** (`GET users`): there is no account listing (ADR-0012); the search by name, with its guardrails, takes its place.
- **Session state by identifier** (`GET user-sessions/by-user-identifier/{identifier}`, `GET user-sessions/{eventId}/by-user-identifier/{identifier}`, the delete by Event and id, and the bulk delete): the state is the caller's own, and nobody reads or removes another person's by an identifier.
- **Print** (`POST print/pdf`, `POST print/zip`): printing is the browser's (ADR-0011), so no route renders a page.
- **The CORS preflight** (`OPTIONS {*path}`): the Api serves its own pages, so what the Ui sends is of the same origin, and its CORS policy answers only the origins it is configured with, for `GET` and `POST`.
- **Settings** (`GET settings/{accountId}`, `POST settings`, `PATCH settings`): the `Setting` aggregate is deleted, and the rules are fields of the Tenant (ADR-0012).
- **Operators** (`operators`): they are grants of an Event, not a collection of its own (ADR-0012); the capabilities of an Event say what a person may do.
- **The safe delete of a Horse** (`DELETE horses/{id}/safe`): it did what `DELETE horses/{id}` did, and neither asked whether a Participation used the Horse. The delete of an Athlete or a Horse in the Api does (409 `athlete-in-use`, `horse-in-use`).
- **Removing many at once** (`DELETE` of a collection with a body of rows): JSON:API has no request that removes many, so a client removes them one at a time.
- **The lists and verbs of an Event's life** (the two lists, and the verbs that started, ended and reset an Event, which went with a stored flag): the Api starts an Event (`POST /api/events`) and resets it (`DELETE /api/events/{id}`), and an Event is over when its last day is.
- **Snapshot results**: gone (ADR-0005); what became of a Snapshot is the outcome of its time event.

## Done

An endpoint is done when every section above holds for it, it declares what it needs with `[Requires]` (or is on the public list) and takes its caller from the `AccessContext`, every failure path returns a `code`, and an integration test covers one success and one rejected request, and where the request names a place, the order of the answers.
