# An Athlete and a Horse are registered once, and every copy carries their Id

Status: proposed

A Participation embeds the Athlete and the Horse it was entered with, and the configure event an Event started from embeds them again, so one person or animal exists as dozens of copies with nothing tying them together: ids that were minted per copy or are 0 (ADR-0009), names in Bulgarian in some Events and in Latin in others, and a FeiId on a minority. Setup holds 60 Athletes and 71 Horses; the finished Events hold about 170 and 195 distinct ones. Nobody can ask what an Athlete or a Horse has ridden. We now register an Athlete or a Horse once, in Setup, and every copy carries that row's Guid and keeps the names as entered. A one-off migration builds the registry from the data that exists, and Setup stops new duplicates from appearing.

## What follows from it

**The registry is Setup.** Every Athlete and Horse has exactly one row in `athletes` or `horses`, including those that exist today only as copies; the migration creates those rows from the latest copy, and Setup rows that are the same person are merged into one. The Id of a copy equals the Id of its row, as the Id of a Core Event already equals its configure event's.

**Copies keep names as entered.** The migration rewrites ids and nothing else in Core: a finished Event reads as it was printed, which is also why live references from Participations to Setup stay deferred (ADR-0006). Setup rows change otherwise only to fill an empty NameEnglish.

**What counts as the same.** Matched automatically: the same FeiId (an Athlete's compared as a number, a Horse's trimmed and case-folded); an exact name after trimming, collapsing spaces and case-folding, compared across Name and NameEnglish of every copy; the same name under the official Bulgarian-to-Latin transliteration; and the same legacy id other than 0. A match on FeiId or legacy id whose names share nothing is a conflict, not a match. Sent to review: looser spelling variants (ю as yu or u, я as ya or ia), near-misses of one or two edits, and conflicts, such as equal names with different FeiIds, where the whole group is held. Country is shown as evidence and is never a veto: Bulgaria is entered as both BGR and BUL. Horses follow the same rules with no extra corroboration, because the pool is small. The owner decides review items in a decisions file; items left undecided stay separate identities.

**A migration, not a feature.** `migrate-identities` (ADR-0009) is a dry run unless told to apply. It writes its report and reads its decisions outside git, because both hold real names; it is idempotent, so it can be run until nothing is left to decide and it finishes after an interruption; and it ends with a read-only verification. It is deleted after deploy, like the other migrations. The matching rules live in one domain service so that Setup and the search use the same ones.

**Setup prevents duplicates.** An Athlete or Horse that any Participation refers to cannot be deleted, and creating or renaming one whose name (in any script) or FeiId exists warns and offers the existing row. `Athlete.User` is retired: it points from the Athlete to a user, nothing reads it, and the user's own link to an Athlete lives with the user.

**Reading by Athlete or Horse needs sign-in.** The registry makes one person's whole record queryable, which per-Event Results never were. The Participations of an Athlete or of a Horse, the Search that finds them and the Profile that holds them are served to signed-in users only, enforced by the API and hidden from anonymous visitors in the UI. That is an exception to the public reads of ADR-0001, and the privacy policy has to cover it: the Junior and Young Rider categories include minors.

## Considered options

**Live references from Participations to Setup** (ADR-0006's deferred option). Gives the same stable identity, but changes what finished Events show whenever Setup changes. Still deferred.

**A separate collection of people and horses.** Two registries to keep in step with Setup's pick lists, for rows Setup already has: names, FeiId, Country.

**Merge only on FeiId and exact names.** Safest, and leaves about thirty pairs that are plainly the same, a name in both scripts, to hand review. The pool is small enough that the owner chose confidence for strict transliteration and review for everything looser.

**Anonymous reads.** Consistent with ADR-0001, but anyone could assemble a person's record, minors included.

## Consequences

Judge's pick lists grow from the Setup rows to everyone who ever competed. A wrong merge puts one person's rides on another's page and is undone only from the backup, which is why anything looser than a FeiId, an exact name, strict transliteration or the same legacy id waits for the owner. Review items still undecided when the tool is deleted stay separate; merging them later is a Setup feature, not a rerun. The migration runs last in the cutover (ADR-0009), after the copies migration of ADR-0006, so Rankings and Handouts already hold references and only Setup, the configure events and the Participations are rewritten.

Any endpoint this decision adds or changes follows `.claude/skills/rest-api/SKILL.md` (ADR-0008).

## Amendments

ADR-0012 settles the scope of the registry: one row per Athlete, Horse, Club or Official across all Tenants, owned by the Tenant that registered it. Other Tenants reference it by Guid through the cross-tenant search and cannot edit it, and the duplicate warning spans Tenants.

## Readings made when the matching and the guards were built (#635)

- **One domain service, three keys.** `NTS.Domain.Setup.Services.Identities` holds the rules, pure: `IdentityNames` (the name normalised, in Latin letters by the official Bulgarian-to-Latin system, folded to the looser key, and the words of that key in one order), `IdentityFeiIds` and `IdentityMatcher` (`Classify` a pair, `Among` many for a form, `Group` a set of copies). The class that decided is reported (`MatchClass`): same FEI ID, exact name, strict transliteration, same legacy id are automatic, in that order of precedence; spelling variant, near-miss and conflict are for a review.
- **What is a conflict.** Equal names (exact, by transliteration or by the looser key) under different FEI IDs; a FEI ID or a legacy id that two copies share while their names share nothing (not even a near-miss); and a legacy id that two copies share under different FEI IDs. Two different FEI IDs under names that are only a near-miss are two people, and are not listed. A FEI ID or legacy id match under names that are a near-miss is still a match. A zero FEI ID (any number of zeros) is no FEI ID for an Athlete and for a Horse. A legacy id is given to the service as the text of the number (ADR-0009 allows no integer identifier in our code): its zeros do not count and 0, blank and none are no id.
- **The looser key** folds what the ADR names and the common spellings of the same letters: a mark on a letter goes; ц as ts, tz or c is c; щ as sht or shch is sht; х as h or kh is h; ю as yu, iu, ju or u is u; я as ya, ja, ia or iya is ia, a doubled i being one; what is left of й as y or j is i; x is ks, w is v. ж is not folded (Yana and Zhana stay two names). A hyphen is a space; a dot or an apostrophe goes. The key of a key is the key.
- **A near-miss** is at most two edits of the words of the looser key taken in one order, and fewer edits than half the length of the shorter key, so that two short Horse names (Max and Mia) are not a near-miss of each other and the review is not filled with them. The same words in another order are a near-miss (distance 0). Say if the owner wants exactly two edits whatever the length.
- **A group** is what automatic matches join through any chain, so a Setup row that has both scripts joins a copy in Cyrillic only and a copy in Latin only that match nothing alone. A group that holds two copies that disagree is held whole. A review item is a pair of groups with something alike between them, told by the strongest of the classes between them (a conflict, then a spelling variant, then a near-miss). The same copies in the same order give the same groups.
- **The registry form warns, and names the row.** It warns of a row with the same FEI ID, of one with the same name (the same text, or the same name in the other script) and of one with a similar name (a spelling variant); a near-miss is not a warning. A row is named with its FEI ID and whether it is another Tenant's. The other Tenants' rows are those the cross-tenant search finds for the text that was typed, so one in another script is found where the row has its name in that script too (its name and its name in English); a key stored with the row that makes the other spellings of the same letters one is #651. There is no picker in the registry form: to offer a row is to name it.
- **A row that a Participation refers to is not deleted.** The Api refuses with 409 `athlete-in-use` or `horse-in-use` when a Participation of any Tenant, of an Event that has started or of one that has not (its Setup), holds a copy with the id of the row. The row is found among the Tenant's own first, so another Tenant's row is 404 whether it is named or not. The Krud lists ask the service what is there after a delete, so a row that was refused stays in the list and the person has been told why.
- **`Athlete.User` is retired.** The domain property, the model member and the form's carry of it are gone; a stored `User` of an older document is ignored on load and left as it is by an edit, and the legacy Functions host no longer sets it.


## Readings made when the dry run was built (#636)

- **A spelling is the unit.** Copies that agree on the legacy id, the name, the name in English and the FEI ID are one spelling, however many documents hold them, and the matching is done once for them. A Setup row is always a spelling of its own, so that Setup duplicates stay countable. Country and Club are evidence for the report and are not part of a spelling. A copy with no name at all is listed and set aside.
- **The counts.** An identity that has no Setup row is a row to create, and its copies are the copies whose Setup row is gone; an identity with more than one Setup row is a duplicate, and the rows beyond the first are the ones that would merge. A Participation that two Rankings of before ADR-0006 copy is one ride, whatever the number of copies.
- **The key of a decision** is made of the normalised spellings of the two groups of an item (trimmed, spaces collapsed, lower case, in order) and their FEI IDs, the smaller group first: `athlete (fei 100): stefan kolev <> athlete (fei 101): stefan kolev`. A held group is decided under the key of the group alone. A database id is never in a key.
- **The decisions file** is `{ "rules": { <class>: <word> }, "items": { <key>: <word> } }` with the word `same`, `different` or empty, and the classes `Held`, `Conflict`, `SpellingVariant` and `NearMiss`. An item's own word beats the rule of its class. The dry run writes every item still to decide with no word, keeps everything the owner wrote, and reports a key that matches nothing in the data and a `different` that other decisions of `same` overrule.
- **A held group is decided whole.** `same` makes all of it one; undecided, or `different`, every spelling of it stays apart, which is the rule that items left undecided stay separate identities. A `same` for a pair next to a group that is held and undecided waits for it, and is reported.
- **The days of an Event** that the report names are the days of its place, not the UTC dates of the instants it is stored as, so that the report is the same on any machine.

## Readings made when the history of a Participant was built (#638)

- **A Participant is an Athlete or a Horse** (CONTEXT.md): the umbrella term for the two kinds of row of the registry, which the search, the history and the links share. A Participation stays the act of Participants competing, with its phases and outcome.
- **A line of the history is composed, never stored.** It is made whenever it is asked for from the Participation, its Event and the Rankings that count it (ADR-0006), over the rides the id of the registry row finds in any Tenant, so that what a Ranking stores or the Results rank is what the history shows. The Events and their Rankings are read by the ids of the Events the rides name; no index serves the Rankings by Event, because the collection holds a few Rankings for each Event. A history is a page made by the database, which joins the rides with their Events, filters, sorts and cuts them (below), and only the rides on the page are composed. Only the Events that have ended have lines (ADR-0007): a Live Event has no final placings yet. A Participation or an Event that the Functions host flagged as deleted is not a ride.
- **The ride's own Ranking** is the one that carries the name, the ruleset and the Category of the ride, which is how the start of an Event made it; the other Rankings that count the ride, the Main Operator's own ones, are listed with the placing it has in each. A Ranking of the Main Operator's that happens to share all three is not told from the first (the first by name, Category and id is the one).
- **A placing** is the elimination as the Results show it, or not ranked, or the rank of the entry: the rank the Ranking stores once it holds its final placings, whatever the times would rank the ride now; while it holds none, the rank the Results give it, composed in memory over the Participations of the Event, and 1 for its only entry, which the Results leave unranked. A placing that cannot be told (a Ranking that counts a Participation that is not there, a document the domain does not accept) is left out and the ride is listed all the same.
- **The names of the other half** are told as the displays tell them: in English for a FEI Competition and for a request in English, as they were entered otherwise.
- **The search was made in memory at first, and is not any more.** It read the names of every Athlete and Horse of every Tenant for each search and matched them by the looser key of #635. It is made by the database now, and the registries are searched one at a time: see the readings made when it was moved, below.
- **The links of a person** are one document for each account, `user_links`, which belongs to the person and to no Tenant. They are made and taken away by the routes of the Athlete and of the Horse (`/api/athletes/{id}/link`, `/api/horses/{id}/link`), each by one write of its own, and read by the profile. They name rows of the registries, which any Tenant may link to; a person is one Athlete at a time, so linking another moves the link, and adds at most a hundred Horses. A link is a bookmark: nothing is granted by it, and any signed-in account may link any Athlete.
- **Reading by a Participant needs sign-in everywhere it can be asked.** A list of the public Participations of an Event that filters by the Athlete or the Horse of the Combination is 401 for a visitor, as the history is, so that the public list cannot be used to look a Participant up. The Participations are indexed by the id of the Athlete and of the Horse they copy.

## Readings made when the Participations were built in the Ui (#639)

- **The pages are for people who are signed in, and the drawer offers them to nobody else.** The profile and the search for a Participant (`/participations`) are routes the Ui sends a visitor to sign in for (`WitnessRoutePolicy`), the entries of the drawer ("My Participations", "Search") are rendered for an account that is signed in alone, and the Api answers 401 whatever the Ui shows.
- **One list, used three ways.** The Participations of a Participant are one component that is given a kind and an id: inline for the Athlete of the profile, in a dialog for a Horse, and under the search. It reads the history a page of twenty at a time and a Participation only when its row is opened, so that the Phases and the totals are the ones the Results show, with a line for each other Ranking that counts it.
- **The Horses of a person are derived and added.** The ones their Athlete has ridden are the other halves of the whole history of the Athlete (read in pages of 500, once each, the latest ridden first): there is no route for them, and they are not removable. The ones they added are their links, and are. A Horse that is both is shown once, and is removable, as its link is.
- **The search asks the registry of a kind.** The picker of the Athlete and the picker of the Horses of the profile each ask their own registry, and the search page asks both and shows two lists (below). A picker asks after a pause of 700 ms and for a word of at least two characters, because each search is drawn from the budget of the account, and shows the first page of what it finds.
- **The language is the app's.** Names are told in the language of the request, so the Ui sends the culture the app is in as `Accept-Language` with every request, and not what the browser would send of its own.
- **The day of an Event is the day of its place.** An Event is stored as the instants at which its first and last days start and end where it is, and the Api tells instants in UTC, so the date of the instant is the day before for a place that is ahead of UTC. A row shows half a day on from the first instant (the rule of the migration report above), which is the same day for every viewer.

## Readings made when the search was moved into the database (follow-up of #638 and #639)

- **A search is a list, and the database makes it.** `GET /api/athletes/all-tenants` and `/api/horses/all-tenants` (and the views of the Clubs and the Officials, and the search of accounts) take `filter=contains(name,'text')`, `sort=name` or `sort=-name`, and the pages of every list, ten rows to a page and twenty-five at most, with `meta.page` and `links.next`. Nothing is read into the Api to be matched, sorted or paged. `/api/participants`, which read both registries whole and did it in memory, is gone. The Athletes and the Horses are two registries and so two searches: the pickers of the profile ask the registry of their kind, and the search page shows the Athletes and the Horses as two lists, each with "Show more". Participant stays the word for an Athlete or a Horse in the glossary and in the Ui; the Api has no resource of that name.
- **The match is a regular expression that is not case-sensitive, not OData's `contains`.** `contains` is case-sensitive and `tolower` lowers the case of ASCII letters alone in MongoDB, so neither finds "иван" in "Иван", while a `$regex` with the `i` option matches Cyrillic. Every word of the text (six at most) has to be part of the name, the name in English or the FEI ID of the row, in any order, and a word is escaped and never a pattern. The route builds it (`NameSearch`); the one term that is a search is not handed to the OData translator.
- **A name is found in the script it is registered in, and in English where the row has its name in English.** The looser key of #635 is not used by the search any more, so a spelling of the same letters that the row does not have (Yordan, Iordan, Jordan) is not found by another, and the Latin and the Cyrillic names sort apart. `migrate-identities` fills the name in English where the spellings differ (#637), which is what lets a Latin text find a Cyrillic name. A key stored with the row, made by the same service, would tolerate the spellings and sort the scripts together; it is #651, a convenience that nothing delivered here needs.
- **A page is a search.** Each page draws on the budget of searches of the account (30 in ten minutes), so the search page, which asks two registries, spends two. The minimum of two characters (three until the owner lowered it on 2026-10-23, because a name such as Li Wu is made of short words) is for the longest word and not for the text, or a text of short words would list the registry, and a text has six words at most. The order is the name and then the id, so that rows with the same name are never twice or missing between two pages.
- **What was answered is not asked again.** The Ui keeps the answers of the session (`ParticipantSearchMemory`, fifty of them, each for a minute): the same words in any order and case are one search, a page that was read is remembered by its number, and a text that only grows (a word that gets longer, a word that comes with it) from an answer that is complete (page 1 with no next page) is answered from those rows, narrowed by the words with no request, because every row of the longer text is among the rows of the shorter. The rows keep the values the Api matched (the name, the name in English and the FEI ID) so that the narrowing matches as the Api does, and the name a person reads is made when it is asked for, in the language of the app then. A minute is as long as an answer is kept because a registry row can be added in the same session; the searches of the Console keep their own memory.
- **The history of a Participant is a page made by the database too, joined to the Events.** Its order is the last day of the Event, which is not on the Participation, so the database joins the Participations of the Athlete or the Horse (`$lookup` of the Event, which MongoDB 8 on Atlas has) with the Events that have ended, filters and sorts the rows by the members of a ride and an Event (`HistoryRide`, newest Event first, the id of the ride after the sort so that no ride is twice or missing between two pages) and cuts the page. The placings, the other half of the Combination and the other Rankings that count a ride come from the Rankings, and are composed for the rides of the page alone, with the Participations, Events and Rankings they need. A document of a ride outside the page is never read.
- **A filter that the database cannot run on a row is 400 on every list, not 500.** A division by zero, or a part of a text that starts past its end, is valid in the grammar and fails when the database runs it on a row, or when the driver evaluates what does not depend on one. A 500 is for what the caller did not cause, so every list reads its page through one place (`ReferencePages`), and the exception of a read that failed while it applied a caller's filter tells whose the failure is (a sort is a list of members, which the database always runs). The error that the driver meets in a part of the expression that has no row (`1 div 0`, a `TargetInvocationException`) and a command that the database refuses for the query (a bad value, a type mismatch, a failed parse, an overflow, a failed conversion, or one of the numbered assertions of its expressions, which it names `Location` and the number) are the expression's: 400 `invalid-filter`. A connection that is lost, a wait that ends, rights, and a command refused for the state of the server (not primary, shutting down, a time limit) are the database's: 500.
